1 · Explain it aloud

Answer each one out loud, as if to a teammate who has never seen the repo. Aim for 30–60 seconds each, then open the model answer.

"Why did we move logs off Elasticsearch?"

Model answer

That Elasticsearch cluster also serves product search, and the old Winston transport made a blocking network call per log line. So a burst of logs could slow down customers searching the catalogue. Now services write JSON to stdout and Alloy ships it to Loki, off the request path. Elasticsearch is reserved for search. (ADR 0001, first paragraph.)

"Walk me through one login, from the request to Grafana."

Model answer

The request arrives, and the HTTP instrumentation starts a SERVER span (continuing any incoming traceparent) and makes it active. The middleware puts its trace ID in x-trace-id. Mongoose and MongoDB add CLIENT spans. logger.warn reads the active span, stamps trace_id, redacts, and writes one JSON line to stdout. Alloy tails it, makes level/service labels and trace_id structured metadata, and pushes to Loki. Meanwhile, the ended spans are batched, redacted and pushed over OTLP to Alloy, then to Tempo. In Grafana, a derived field links the log line to its trace, and traces-to-logs links back.

"What's the one rule about Loki labels?"

Model answer

Labels must have few possible values, because every combination is a separate stream in the index. So only level and service. Anything per-user or per-request (userId, trace_id) stays in the line or in structured metadata.

"What happens if the collector is down?"

Model answer

Requests carry on normally. Logs don't need the network at all. Spans sit in a bounded batch queue and are dropped when exports fail. We accept losing telemetry to avoid losing requests. There's a test for it, and you watched it happen in Lesson 6.

"Why these choices and not the alternatives?"

Model answer

A separate log-only Elasticsearch fixes the coupling but still has no traces or metrics, and links signals poorly. SaaS adds cost and an external dependency to a lab, and since we speak OTLP we could switch later by reconfiguring only the collector. Services pushing to each backend directly would couple every service to backend addresses and leave redaction and sampling without a central home. (ADR 0001, "Considered Options".)

2 · Review a PR: ship or block?

A fictional PR for ticket 05, "roll tracing out to cart". Some hunks are fine and some should be blocked. Decide every one, then check.

For each hunk: would you approve it as it is?

  1. cart/src/index.ts 
    +import app from './app';+import './tracing'; import { dbClient } from './db';

    Block. app loads Express before the SDK starts, so the traces silently lose their spans. ./tracing must be the first import (Lesson 5).

  2. cart/src/tracing.ts 
    +import { startTelemetry } from '@ecom-micro/common';

    Block. The main entry loads Express. Import from the @ecom-micro/common/telemetry subpath instead.

  3. cart/src/tracing.ts (the logger uses 'cart-service') 
    +export const telemetry = startTelemetry({ serviceName: 'cart' });

    Block. service.name must equal the logger's service, or trace → logs silently finds nothing (Lesson 6).

  4. k8s/observability/alloy.yml, stage.labels 
       level   = "",   service = "",+  user_id = "",

    Block. High cardinality: one stream per user (Lesson 1). Keep it in the line and filter with | json.

  5. cart/src/controllers/addItem.ts 
    +logger.info('Item added to cart', { userId, productId, quantity });

    Ship. These are structured fields in the line body, which is exactly where high-cardinality IDs belong. Nothing here is secret.

  6. common/src/queues/basePublisher.ts 
    -Buffer.from(JSON.stringify(data))+Buffer.from(JSON.stringify({ ...data, traceparent }))

    Block. ADR 0001: trace context goes in AMQP headers, never the payload. This changes every event contract.

  7. common/src/observability/telemetry.ts 
    -return new BatchSpanProcessor(new RedactingSpanExporter(new OTLPTraceExporter()));+return new SimpleSpanProcessor(new RedactingSpanExporter(new OTLPTraceExporter()));

    Block. The Simple processor exports every span the moment it ends: one network call per span, no batching, and the redaction runs inside the request. Simple is only for the test seam.

  8. cart/src/controllers/checkout.ts 
    +console.log('checkout body', req.body);

    Block. console.log bypasses redaction. Card data or tokens in the body would reach Loki in plain text (Lesson 3).

  9. common/src/middleware/errorHandler.ts 
    -console.log(err);+logger.error('Request failed', { error: err });

    Ship. This fixes the Lesson 1 puzzle: the error becomes one structured, redacted JSON line with a trace_id, instead of an unlabelled stack trace.

  10. k8s/observability/grafana.yml, tracesToLogsV2 
    -query: '{$${__tags}} | trace_id="$${__trace.traceId}"'+query: '{${__tags}} | trace_id="${__trace.traceId}"'

    Block. Without $$, Grafana expands these as environment variables at startup, which leaves them empty, and the link breaks silently (Lesson 6).

3 · Walk an incident

Say each step before opening the answer.

"Login was really slow for me at about 10:40." Plus a screenshot showing x-trace-id: 7c1e…

Model walk-through
  1. Tempo → TraceQL → paste the ID. (No ID? Search { resource.service.name = "auth-service" && duration > 1s } around 10:40.)
  2. Read the waterfall: is the time in the Mongo CLIENT spans (database), or in a gap under the handler (our own code, such as bcrypt)?
  3. Click Logs for this span for everything that request logged, including any warnings.
  4. For scope, check whether it's just this one request. sum by (level) (count_over_time({service="auth-service"}[5m])) around 10:40 shows whether errors spiked.

"The trace ID in this log line says 'trace not found' in Tempo."

Model walk-through

Four innocent causes, from most to least likely: it's older than Tempo's 72 h retention; it was sampled out (an upstream traceparent with flags 00); it was dropped during a collector outage; or the spans haven't arrived yet (the batch delay plus Tempo's block cut, so wait a minute). Only after those, suspect a bug.

"webhook_pending checkouts." (Ticket 06 onwards)

What you can and can't do today

Not yet: order isn't traced or on the new logger until later tickets. Once it is, you'd search Loki for {service="order-service"} |= "webhook" and follow the trace from the payment request. When the tracing tickets land, the context-propagation skills from Lesson 5 are what will link the Stripe webhook to the order's events.

In short: the whole course in 3

  1. Logs go to stdout; spans are pushed to Alloy. Only Alloy talks to Loki and Tempo, and a dead collector costs telemetry, never requests.
  2. One trace ID ties everything together: it's active in-process, carried by traceparent, stamped on logs, returned in x-trace-id, and linked in Grafana.
  3. Guard the invariants: few labels, logger-only output (redaction), tracing imported first, one service name everywhere.
