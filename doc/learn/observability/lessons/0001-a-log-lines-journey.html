Lesson 1 · Ticket 02 · ~20 min

A log line's journey

By the end you'll have found your own failed login in Grafana and be able to name every hop it took to get there, along with the file that controls each hop.

Why this exists

Before ticket 02, auth sent its logs straight to the Elasticsearch cluster that also powers product search. That meant a network call on every log line, and a burst of logs could slow down customers searching the catalogue. Most other services just wrote unstructured console.log text, so you couldn't filter anything. (spec, Problem Statement)

Observability means you can work out why the system is misbehaving from the outside, using data it gives off, without adding new code first. That data is called telemetry, and it comes in three kinds: logs, traces and metrics (OpenTelemetry primer). This lesson covers only the first one.

1 · A structured log line

This is a real line from your cluster, written when someone tried to log in with an unknown email:

{"timestamp":"2026-09-27T04:59:32.457Z","level":"warn",
 "service":"auth-service","version":"1.0.0","environment":"local",
 "trace_id":"f88743982cd192ec906042c8d4491502","span_id":"83844f5519732271",
 "message":"Login failed","reason":"unknown_email","email":"n***@example.com"}

It's structured: one JSON object per line, with the same keys in the same order every time. A machine can filter on level or reason without guessing at free text. The code that produced it is a single line in auth/src/controllers/loginUser.ts:

logger.warn('Login failed', { reason: 'unknown_email', email });

The logger from createLogger (common/src/observability/logger.ts:135) did three things to that call:

masked the email
the redaction step turned nobody@example.com into n***@example.com. Lesson 3 covers redaction.
stamped the fixed fields
timestamp, service, version and environment are always present, and a caller can't overwrite them.
added trace_id / span_id
these link the line to a trace. Ignore them until Lesson 4.

2 · Where the line goes

Here's the key design choice: the app never sends its logs anywhere. It prints them to stdout and stops there (logger.ts:168). This follows the Twelve-Factor rule that an app "never concerns itself with routing or storage of its output stream" (12factor.net/logs). Because the app never waits on a network call, a down log backend can't slow a request (ADR 0001).

The step to understand best is Alloy, the collector. It runs as a DaemonSet (alloy.yml:185), meaning one copy on every node, and each copy tails only the pods on its own node, so no line gets shipped twice. For each line, it runs:

  1. stage.json (line 109): reads level, service and trace_id out of the JSON.
  2. stage.labels (line 119): makes only level and service into labels.
  3. stage.structured_metadata (line 130): attaches trace_id, pod and namespace to the line without making them labels.
  4. loki.write (line 142): pushes the result to Loki.

3 · Labels vs everything else

This is the one idea from this lesson you need to remember:

Loki groups lines into streams, and each unique combination of label values is its own stream. Loki indexes only the labels, not the text of the line. Labels must therefore have few possible values (low cardinality). In the Loki docs' words, high cardinality "causes Loki to build a huge index and to flush thousands of tiny chunks" (Understand labels).

So level (about 7 values) and service (about 10) are good labels. A userId or trace_id label would create a new stream for every user or every request. Those stay in the line body, where | json can still filter on them, or in structured metadata. Expect this question in every PR for tickets 04 and 15.

4 · Lab: find your own login

  1. Make a log line. Try to log in with an email that doesn't exist:

    curl -sk -X POST https://ecom.dev/api/users/login \
  -H 'content-type: application/json' \
  -d '{"email":"lesson1@example.com","password":"x"}'

    You should get a 400 back. That's expected, and it produces the warn line.

  2. Open Grafana. In another terminal:

    kubectl port-forward svc/grafana-srv 3300:3000

    Go to localhost:3300. The login credentials come from the k8s secret (Grafana requires a login and anonymous access is off):

    kubectl get secret ecom-secret -o jsonpath='{.data.GRAFANA_ADMIN_USER}' | base64 -d; echo
kubectl get secret ecom-secret -o jsonpath='{.data.GRAFANA_ADMIN_PASSWORD}' | base64 -d; echo

  3. Select a stream. Open Explore, pick the Loki datasource and switch the query editor to Code. Run:

    {service="auth-service"}

  4. Narrow it by label. Now only warnings:

    {service="auth-service", level="warn"}

  5. Filter on a field that isn't a label. reason isn't a label, so parse the JSON first (LogQL docs):

    {service="auth-service"} | json | reason="unknown_email"
    Checkpoint: what does the email field show, and why?

    l***@example.com. The logger masked the email before the line ever left the process. Loki never saw the real address.

  6. Puzzle. Run this and look at what comes back:

    {service="auth"}
    Why are there lines labelled auth, not auth-service?

    They're lines of a stack trace, printed as plain text, one line at a time. common/src/middleware/errorHandler.ts:6 does console.log(err) on every error, bypassing the logger. With no JSON, stage.json finds no service field, so Alloy falls back to the pod's app label, which is auth. You've just found a real gap: that output isn't structured, isn't redacted and has no trace_id. It's a good one to raise in a later ticket.

5 · Check yourself

Answer from memory first, then click. A wrong pick can be retried.

Where does the auth service send its log lines?

Only stdout. Alloy reads it from the Kubernetes API, so the app has no network dependency for logging.

Which component decides that level becomes a Loki label?

stage.labels in alloy.yml. The logger only writes JSON fields; it has no idea what a label is.

A PR adds userId to Alloy's stage.labels. What's the main problem?

Cardinality: one stream per user makes the index huge. Keep it in the line and filter with | json | userId="…".

Loki is down for ten minutes. What happens to login requests?

The request path only writes to stdout. The delay and buffering happen in Alloy, off the request path. That's the point of ADR 0001.

With LOG_LEVEL=warn, does "User logged in" (an info line) reach Loki?

The logger drops entries below its level before they're written. It's set in k8s/config/app-config.yml, so you can change it without touching code.

Stuck or curious?

Ask me anything: "why a DaemonSet?", "what's in loki.yml?", "show me the redaction code". Followup questions are the fastest way through this. When you're ready, say so and I'll check what stuck before Lesson 2.

In short: remember these 3

  1. The app only writes to stdout. Alloy collects the lines and sends them to Loki. A broken log backend can never slow down a request.
  2. Labels must have few possible values. Only level and service are labels. Things like userId stay in the line.
  3. trace_id links a log line to its trace. (Lessons 4–6.)

If you forget everything: app → stdout → Alloy → Loki. The other two follow from it.

You don't need to memorise the YAML files, the Alloy stage names or the LogQL syntax. Look them up in the cheat sheet and the glossary. The k8s config will feel dense on a first read; it gets clearer on the second and third.
