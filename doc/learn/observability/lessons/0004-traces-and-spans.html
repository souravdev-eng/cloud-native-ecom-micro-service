Traces and spans

By the end you'll have taken the x-trace-id from one of your own logins, opened that trace in Tempo, and read its waterfall: which step was the database, and where the time really went.

Why this exists

A log line tells you that something happened. It can't tell you where the 800 ms of a slow login went: the database, the password hash, or something else. A trace can. It's "the path of a request through your application" (OpenTelemetry: Traces), recorded as timed steps.

1 · The vocabulary: four words

span
"A unit of work or operation": one timed step, with a name, a start and end time, and key-value attributes (for example http.response.status_code = 200).
trace
All the spans that share one trace ID (32 hex characters), arranged as a tree.
parent / root
Each span points at its parent span's ID. The one with no parent is the root, where the trace started.
kind
SERVER: an incoming request. CLIENT: an outgoing call, including a database call. INTERNAL: work inside the process, like Express middleware.

A span also has a status: Unset (the default, meaning fine), Error, or Ok. That's the field the error-trace sampling in a later ticket will key on.

2 · What a login looks like

This is roughly the waterfall Tempo draws for a successful POST /api/users/login. Each bar is one span; its position and length show when it ran within the whole request.

POST /api/users/loginSERVER
middleware - jsonParserINTERNAL
request handler - /api/users/loginINTERNAL
mongoose.User.findOneCLIENT
mongodb.findCLIENT

Illustrative. Your span names may differ slightly by library version; the lab shows the real ones.

Read it like this:

  1. The root is the SERVER span: the whole request, from arrival to response.
  2. The Mongo lookup is two nested spans: Mongoose (the ODM you call) wraps the MongoDB driver (which talks to the database).
  3. Look at the gap after the Mongo spans: most of the handler has no child span under it. That time is your own code. Here it's bcryptjs comparing the password (compareDBPassword.ts), which is pure JavaScript, so no library records it.

Reading tip: a parent with a long bar and short children means the time is spent in the parent's own code. To see inside that gap, you'd add a custom span (getServiceTracer arrives in ticket 04). You wouldn't add more logs.

3 · Where spans come from, and where they go

Nobody wrote those spans by hand. The telemetry bootstrap in telemetry.ts (startTelemetry) turns on auto-instrumentation: plugins that patch popular libraries so every request and query creates a span automatically.

const instrumentations = [
  new HttpInstrumentation(),      // → the SERVER span
  new ExpressInstrumentation(),   // → middleware / handler spans
  new MongoDBInstrumentation(),   // → mongodb.find
  new MongooseInstrumentation(),  // → mongoose.User.findOne
  new PgInstrumentation(), new IORedisInstrumentation(),
  new RedisInstrumentation(), new AmqplibInstrumentation(),
];

Auth doesn't use Postgres or Redis. The list is shared by every service, and an unused plugin does nothing.

When a span ends, it travels a path that should look familiar from Lesson 1, with one difference: spans are pushed over the network, not written to stdout.

auth: span ends
  → BatchSpanProcessor        queues it, sends in batches (telemetry.ts)
  → RedactingSpanExporter     masks secrets (Lesson 6)
  → OTLP/HTTP  → alloy-srv:4318            OTEL_EXPORTER_OTLP_ENDPOINT
  → Alloy: otelcol.receiver.otlp → processor.batch → exporter.otlp
  → tempo-srv:4317 → Tempo (72 h retention)  k8s/observability/tempo.yml
  → Grafana Explore, Tempo datasource

OTLP is OpenTelemetry's own wire protocol. The endpoint comes from one line of shared config in k8s/config/app-config.yml:

OTEL_EXPORTER_OTLP_ENDPOINT: 'http://alloy-srv:4318'   # the Alloy Service from Lesson 2

Auth only knows Alloy's address, never Tempo's. That's the ADR 0001 rule "services never push directly to each backend".

The handle: x-trace-id

How do you find your trace among thousands? The small middleware in traceIdHeader.ts puts the trace ID on every response:

const ids = activeTraceIds();
if (ids) res.setHeader('x-trace-id', ids.traceId);

A bug report or a devtools screenshot now carries the key to the full trace. (Auth mounts it first in app.ts; ticket 04 folds it into mountObservability.)

4 · Lab: open your own login

  1. Log in and keep the header. Use the user from Lesson 3 (-i prints the response headers):

    curl -sk -i -X POST https://ecom.dev/api/users/login -H 'content-type: application/json' \
  -d '{"email":"lesson3@example.com","password":"Secret#123"}' | grep -i x-trace-id

    Copy the 32-hex value.

  2. Open it in Tempo. In Grafana Explore, pick the Tempo datasource, choose the TraceQL tab, paste the trace ID and run it.

  3. Read the waterfall. Click the root span, then open its Attributes.

    Checkpoint: find these three things

    (1) http.response.status_code on the root span: 200. (2) The Mongo CLIENT span(s) and their duration. (3) The gap in the handler, which is bcrypt. Is it bigger than the database time? For a login it usually is, and that's by design: password hashing is meant to be slow.

  4. Search instead of paste. TraceQL puts conditions on spans inside { } (TraceQL docs). Try each one:

    { resource.service.name = "auth-service" }
{ resource.service.name = "auth-service" && duration > 50ms }
{ resource.service.name = "auth-service" && span.http.response.status_code >= 400 }

    resource. attributes describe the process (the service), and span. attributes describe one span. Lesson 5 explains where service.name is set.

  5. Compare with a failed login. Log in with the wrong password, open that trace, and look for what's different.

    What changes?

    Status code 400, and there's still a Mongo span (the user exists) and a bcrypt gap. For an unknown email, there's no bcrypt gap: the handler returns right after findOne. That timing difference can itself leak which emails exist, which is a real security topic. The trace just made it visible.

5 · Check yourself

What makes a set of spans one trace?

The trace ID is the only thing that groups them. It can span many services, which is what "distributed tracing" means.

What span kind does a MongoDB query get?

A database call leaves the process, so the service is the client. OTel's docs list "an outgoing HTTP request or database call" as the CLIENT examples.

A handler span is 600 ms, and its only child is 40 ms. Where did the time go?

Uncovered time belongs to the parent. Export happens after the span ends, off the request path, so it can't show up inside a span.

Where does auth send its spans?

OTEL_EXPORTER_OTLP_ENDPOINT=http://alloy-srv:4318. Only Alloy talks to Tempo. Logs use stdout; spans are pushed.

From Lesson 3

Which query finds wrong-password lines most cheaply?

A narrow label selector plus a text filter, with no parsing. Two of the others scan every stream; | json alone parses every line and doesn't filter anything.

From Lesson 1

Why is trace_id never a Loki label?

A new value per request means a new stream per request: the high-cardinality problem. It lives in structured metadata instead.

In short: remember these 3

  1. A trace is a tree of timed spans sharing one trace ID. The root is the SERVER span; DB calls are CLIENT spans.
  2. Time with no child span is the parent's own code. Read the gaps, not only the bars.
  3. Spans are pushed: auth → Alloy (4318) → Tempo. The x-trace-id response header is your way in.

If you forget everything: "grab x-trace-id, paste it into Tempo, read the waterfall".

You don't need to memorise the instrumentation class names, the TraceQL syntax or the exact span names. See the traces cheat sheet and the glossary.
