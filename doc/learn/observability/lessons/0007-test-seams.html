Lesson 7 · Tickets 01 + 03 · ~20 min · no cluster needed

Test seams

By the end you'll have deliberately broken the span redactor, watched exactly one test catch it, and put it back. You'll also be able to explain why our telemetry tests check what leaves the process and never how the code works inside.

Why this exists

Ticket 01 came before any observability work, and it didn't add a single feature. It added a way to prove that nothing changed. Tickets 06 onward will rewrite the RabbitMQ publisher and listener to carry traceparent, so the current behaviour had to be pinned down first. Tests that do that are called characterisation tests: "they pin down what BasePublisher does today" (basePublisher.test.ts).

When you review a PR for tickets 04–18, the tests are where you'll check that it does what it says. So you need to be able to read them.

1 · Seams and test doubles

A seam is a place where a test can swap in different behaviour without editing the code under test. What goes into the seam is a test double. Two kinds matter here (Martin Fowler: Test Double):

fake
Has "working implementations, but usually take[s] some shortcut which makes them not suitable for production".
spy
A stub that also records "some information based on how [it was] called".

2 · Our three seams

The spec allowed one test seam in production code. Everything else plugs in from outside.

FakeChannel: a fake RabbitMQ (ticket 01)

common/src/test/fakeChannel.ts stands in for an amqplib Channel. It's both a fake and a spy: it records every call, and deliver() pushes a message into a listener's callback.

const fake = new FakeChannel();
await new ProductCreatedPublisher(fake.asChannel()).publish(data);

expect(fake.assertedExchanges).toEqual([
  { exchange: 'product-service', type: 'direct', options: { durable: true } },
]);

There's no broker, no network and no Docker, so the tests run in milliseconds. Note options?: Options.Publish on each recorded publish: "later AMQP headers such as traceparent" will show up there in ticket 06.

testSpanExporter: the only hook in production code (ticket 03)

startTelemetry accepts one test-only option. Instead of shipping spans over OTLP, it sends them to an exporter the test holds, usually the SDK's own InMemorySpanExporter:

if (options.testSpanExporter)
  return new SimpleSpanProcessor(new RedactingSpanExporter(options.testSpanExporter));

Look at the wrapping: the test exporter still goes through the redactor, "so the tests see exactly what production would send" (telemetry.ts). A seam that skipped the redactor would let the redaction tests pass against code that leaks.

captureStdout: reading back the logs

The logger's only output is stdout, so captureStdout.ts spies on process.stdout.write and parses the lines: "the only honest way to assert on log output".

The rule behind all three: tests assert on what leaves the process: channel calls, exported spans, stdout lines, response headers. They never assert on private fields. Ticket 01's own acceptance criterion says: "assert only on observable calls to the channel and data handed to onMessage, not on private fields". That's what lets ticket 06 rewrite the internals and keep the same tests green.

3 · Drill: robust or brittle?

Which assertions would survive a refactor that keeps behaviour identical?

  1. expect(fake.published[0].routingKey).toBe('product-created')

    That's what the code asked RabbitMQ to do, which is observable behaviour.

  2. expect((publisher as any).channel).toBe(fake)

    A private field. Rename it and the test breaks, though nothing a user sees changed.

  3. expect(line.trace_id).toBe(span.spanContext().traceId)

    It compares two outputs: the stdout line and the exported span.

  4. expect(redactSpy).toHaveBeenCalledTimes(3)

    It pins how redaction is done (how many calls), not whether the secret is gone. Check the exported attributes instead.

  5. expect(JSON.stringify(attrs)).not.toContain(SECRETS.password)

    It checks the real risk directly, wherever the secret might land.

4 · The tricks in telemetry.test.ts

These look strange at first. Each one exists because of something from Lessons 4–6:

jest.mock('module', …) at the top
Jest hands tests a mock of Node's module built-in, and the SDK's require-hooks would patch that instead of the real one. This puts the real one back so http gets instrumented. (Still, "only http spans are observable under Jest", as CLAUDE.md notes.)
require('express') inside beforeAll
The import-order rule from Lesson 5: load Express only after startTelemetry.
requests via fetch
fetch (undici) isn't instrumented. With http.request, the client would add its own traceparent and overwrite the one the test set.
waitForServerSpan polling
The server span ends on the response's finish event, which can fire just after the client has read the response. Polling avoids a flaky race without a fixed sleep.
a "positive control" test
'exports spans over OTLP/HTTP to the configured endpoint'. Without it, the two "sends nothing" tests would also pass if exporting were simply broken.

5 · Lab: break it on purpose

No cluster needed. Run this from the repo root. It edits real files, so restore them at the end.

  1. Run the suites green first.

    cd common
npm test -- src/observability/__test__/telemetry.test.ts src/queues

    Expect 3 suites and 15 tests passing (checked on 2026-09-27).

  2. Mutation 1: skip the redactor in the test seam. In src/observability/telemetry.ts, inside spanProcessorFor, change

    return new SimpleSpanProcessor(new RedactingSpanExporter(options.testSpanExporter));

    to

    return new SimpleSpanProcessor(options.testSpanExporter);

    Before running: which test will fail? Then run the telemetry test again.

    Result

    Exactly one: ✕ keeps passwords, tokens, auth headers and the ?token= query out of span attributes. The other three stay green. That's what a well-aimed test looks like: one behaviour, one test. It also shows why the seam wraps the test exporter. Without the wrapper, this test would be testing nothing.

  3. Put it back. First confirm that your change is the only one in the file, then restore it:

    git diff src/observability/telemetry.ts     # only your one line?
git restore src/observability/telemetry.ts

  4. Mutation 2: predict it without running. In src/middleware/traceIdHeader.ts, suppose someone writes ids.spanId instead of ids.traceId. Which tests go red? Write your answer down, then check by running it (and restore it the same way).

    Answer

    Two: links the log line, the exported server span and the x-trace-id header… and continues an incoming W3C traceparent…. Both compare the header to the trace ID. A span ID is 16 hex characters, not 32, so neither can pass by accident.

6 · Check yourself

What is a characterisation test for?

It records what the code does now, right or wrong, so a later refactor (ticket 06) can't change it by accident.

Why does testSpanExporter still go through RedactingSpanExporter?

If the seam skipped redaction, the redaction tests would pass even with leaky code. You proved this in mutation 1.

Why does the test require Express inside beforeAll?

Auto-instrumentation patches at load time (Lesson 5). A top-of-file import would load Express too early.

From Lesson 6

Which test proves a dead collector doesn't break requests?

It points the exporter at a closed port, sends several requests, checks each returns 200, and checks that shutdown() settles quietly.

From Lesson 2

In a Kubernetes object, which field holds the state you want?

spec is desired state; status is what Kubernetes reports back.

In short: remember these 3

  1. Three seams: FakeChannel (RabbitMQ), testSpanExporter (spans, the one production hook) and captureStdout (logs).
  2. Assert on what leaves the process, never on private fields. That's what keeps the tests valid through ticket 06's rewrite.
  3. A seam must not skip the thing under test. The test exporter still goes through the redactor.

If you forget everything: "test the outputs; break it once to prove the test works".

You don't need to memorise the Jest tricks in section 4. Reread them when you open telemetry.test.ts.
