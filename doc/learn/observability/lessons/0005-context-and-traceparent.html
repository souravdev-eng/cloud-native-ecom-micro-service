Context and traceparent

By the end you'll have forced auth to join a trace you invented, by sending a hand-written traceparent header. You'll also be able to explain why import './tracing' has to be the first line of index.ts.

Why this exists

Here's a puzzle from Lesson 1. This call never mentions a trace:

logger.warn('Login failed', { reason: 'unknown_email', email });

Yet the line it writes carries trace_id and span_id. Nothing was passed in, so how does the logger know? The answer is context. The same idea, sent across a network, is how one trace can cover several services. Tickets 06 onward depend on it.

OpenTelemetry's definitions: context is "an object that contains the information for the sending and receiving service … to correlate one signal with another", and propagation is "the mechanism that moves context between services and processes" (OTel: Context propagation).

1 · Inside one process: the active span

When the HTTP instrumentation starts the SERVER span for a request, it makes that span active for everything that runs on behalf of that request, even across awaits. Node's AsyncLocalStorage tracks this. It stores data "throughout the lifetime of a web request or any other asynchronous duration", like thread-local storage in other languages (Node.js: Asynchronous context tracking).

So any code, however deep, can ask "which span am I in?". That's all traceContext.ts does:

export const activeTraceIds = () => {
  const span = trace.getSpan(context.active());   // "the span for this request"
  if (!span) return undefined;                    // outside any request
  const spanContext = span.spanContext();
  if (!isSpanContextValid(spanContext)) return undefined;  // all-zero = no trace
  return { traceId: spanContext.traceId, spanId: spanContext.spanId };
};

It has two callers, and both rely on running at the right moment:

the logger (applySchema)
Winston formats run synchronously inside the logger.warn(…) call, so the active span is the caller's own.
the x-trace-id middleware
Sets the header as the request arrives, not as it's sent, because "by then the trace context of an async handler may no longer be active" (traceIdHeader.ts).

Consequence: a log line written outside any request, like "Mongo connected successfully" at startup, has no trace_id. That's correct behaviour, not a bug. Alloy skips the structured-metadata field for those lines.

2 · Between processes: the traceparent header

A process can't see another process's memory, so context has to travel in the request itself. The W3C Trace Context standard defines one header for it (W3C Trace Context):

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └──────────── trace-id ────────┘ └── parent-id ─┘ └ flags
             version (00)       32 hex             16 hex         01 = sampled
trace-id
The trace this request belongs to. The receiver keeps it.
parent-id
"The ID of this request as known by the caller": the caller's span. The receiver's SERVER span becomes its child.
flags
01 means "the caller may have recorded trace data" (sampled). 00 means it didn't.

The HTTP instrumentation reads this header on every incoming request and adds it to every outgoing one. That behaviour, continue, don't replace, is pinned by a test in telemetry.test.ts:

it('continues an incoming W3C traceparent instead of starting a new trace', …
  expect(span.spanContext().traceId).toBe(UPSTREAM_TRACE_ID);
  expect(span.parentSpanContext?.spanId).toBe(UPSTREAM_SPAN_ID);

Looking ahead to ticket 06: RabbitMQ messages need the same thing. ADR 0001 says trace context goes in the AMQP message headers, never in the event payload, so the event contracts in common/src/events/ don't change. The fake channel from ticket 01 already has room for it (options.headers).

3 · Sampling is decided once, at the root

Keeping every trace gets expensive, so some are dropped. Head sampling decides "as early as possible", while tail sampling decides after "considering all or most of the spans within the trace" (OTel: Sampling). The bootstrap uses head sampling:

sampler: new ParentBasedSampler({ root: new TraceIdRatioBasedSampler(sampleRatio()) }),
no incoming traceparent (a root)
Kept with probability OTEL_TRACES_SAMPLER_ARG. The default is 1, which keeps everything.
traceparent present (a child)
Follows the caller's flag, so a trace is "never half-recorded across services" (comment in telemetry.ts).

The spec's cost control is tail sampling in Alloy, which keeps every error and slow trace (a later ticket). Head sampling stays at 100% so that Alloy still has the whole trace to judge.

4 · Why tracing.ts must be imported first

Auto-instrumentation works by patching a library at the moment it's loaded. When Express is required, the SDK swaps in a wrapped version. If Express was loaded before the SDK started, there was nothing to intercept. OTel's own guide: "The instrumentation setup and configuration must be run before your application code" (OTel JS: Getting started).

That's why auth/src/index.ts starts like this:

/** Must stay the first import; see tracing.ts. */
import './tracing';          // ← startTelemetry({ serviceName: 'auth-service' })
import { Channel } from 'amqplib';
import mongoose from 'mongoose';
…
import app from './app';     // ← loads Express

There's a second, subtler rule behind the same bug. startTelemetry comes from a separate subpath, @ecom-micro/common/telemetry. The main @ecom-micro/common entry loads Express (for its middleware), so importing the bootstrap from there would load Express before the SDK starts, which is the same bug in disguise. The header comment of telemetry.ts says it "must stay free of Express, Mongoose, amqplib and the rest of common".

What would you actually see if the order were wrong?

No error at all. The service runs fine, but its traces are thin: the Express handler spans and the Mongoose/MongoDB spans are missing. You might still get the bare HTTP span, depending on load order. It's a silent failure, which is why it's worth checking in every service's entry file when tickets 05+ roll tracing out to cart, product and order.

5 · Lab: join a trace you invented

  1. Send your own traceparent. Make up a trace ID of 32 hex characters (all 1s is easy to spot) and a parent ID of 16:

    curl -sk -i https://ecom.dev/api/users/currentuser \
  -H 'traceparent: 00-11111111111111111111111111111111-2222222222222222-01' | grep -i x-trace-id
    Checkpoint: what should the header say?

    x-trace-id: 11111111111111111111111111111111. Auth continued your trace instead of starting one. If you get a different ID, something in front of auth (the NGINX ingress) started its own trace and replaced the header. That would be worth knowing, so tell me.

  2. Find it in Tempo. Paste 11111111111111111111111111111111 into the TraceQL tab.

    Why does Tempo complain about the root?

    The root span, 2222…, lives in a "caller" that doesn't exist: you. Tempo shows auth's SERVER span with a parent it never received. In real life, that missing parent would be the upstream service, and it would be there.

  3. Predict, then test: an unsampled parent. Same request, a new trace ID and flags 00:

    curl -sk -i https://ecom.dev/api/users/currentuser \
  -H 'traceparent: 00-33333333333333333333333333333333-4444444444444444-00' | grep -i x-trace-id

    Before looking: will x-trace-id be set? Will the trace be in Tempo?

    What happened, and why it matters

    The header is still 3333…: the trace ID exists and is carried on, so log lines get it too. But Tempo has no trace, because the parent-based sampler honoured "not sampled" and recorded nothing. Remember this for debugging: "log has a trace_id, Tempo says trace not found" can simply mean the trace was sampled out upstream.

  4. Read the test that guards import order. Open telemetry.test.ts and find require('express') inside beforeAll.

    Why require there, and not an import at the top?

    Top-level imports run before any test code, which would load Express before startTelemetry: the exact bug from section 4. Requiring it after the SDK starts mirrors the rule services must follow. Lesson 7 covers this test's other tricks.

6 · Check yourself

How does the logger find the current request's trace ID?

trace.getSpan(context.active()). AsyncLocalStorage keeps the request's span active across awaits.

In a traceparent, what does the receiver keep unchanged?

The trace ID stays the same across every hop. The parent-id is the caller's span; the receiver makes a new span that points to it.

Express is imported before startTelemetry runs. What happens?

Patching only happens at load time, so nothing errors. The traces just lack the Express and database spans, which is why it's easy to miss.

Why must trace context go in AMQP headers, not the event payload?

ADR 0001: "Trace context travels in AMQP message headers, never in event payloads. Event contracts stay unchanged." Telemetry stays out of the business data.

From Lesson 4

What span kind is the root of an auth login trace?

The incoming HTTP request is the SERVER span. With your hand-written traceparent, it's no longer the root: your fake caller is.

From Lesson 3

Which query uses structured metadata without parsing JSON?

A | trace_id="…" filter straight after the selector reads structured metadata. {trace_id=…} would need it to be a label, which it isn't.

In short: remember these 3

  1. Inside a process, the active span follows the request (AsyncLocalStorage). That's how logs get trace_id without anyone passing it.
  2. Between processes, traceparent carries it: version-traceId-parentId-flags. Continue it, never replace it. For AMQP, it goes in headers, not payloads.
  3. Instrumentation patches libraries as they load, so import './tracing' comes first and the bootstrap lives on its own Express-free subpath.

If you forget everything: "same trace ID on every hop; tracing loads first".

You don't need to memorise the sampler class names or the flag bits. Just remember: 01 sampled, 00 not. It's all in the traces cheat sheet.
