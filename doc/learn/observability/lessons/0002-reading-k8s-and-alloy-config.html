Lesson 2 · Skill lesson · ~10 min

How to read the platform config

By the end, you'll be able to open any file in k8s/observability/ and know what each part does, which parts to read, and which to skip.

The trick: two languages in one file

Much of the confusion in alloy.yml comes from this: it holds two different languages.

Kubernetes YAML (the outside)
Tells Kubernetes what to run: which container, how many copies, which ports.
Alloy config (the inside)
Tells Alloy what to do once it's running: which logs to read and where to send them. It lives inside the YAML as one big block of text.

Once you know which language you're reading, each one is small.

1 · YAML in five rules

metadata:            # 1. key: value
  name: alloy        # 2. indentation = "belongs to the line above"
  labels:
    app: alloy
ports:
  - name: otlp-grpc  # 3. "-" starts one item in a list
    port: 4317
config.alloy: |      # 4. "|" = the indented lines below are one text value
  loki.write "loki" { ... }
---                  # 5. "---" separates two objects in one file

That's all the YAML you need here. # starts a comment.

2 · Every Kubernetes object has the same shape

Every object in a manifest has four top-level keys (Kubernetes: Objects):

apiVersion
Version of the API. Skip it.
kind
What sort of thing this is. Read this first.
metadata
Its name and labels.
spec
The state you want. Kubernetes keeps working until reality matches it.

Here's a real, complete object from alloy.yml:253, with each line explained:

kind: Service                  # a stable network address
metadata:
  name: alloy-srv              # services call it by this name
spec:
  selector:
    app: alloy                 # send traffic to pods labelled app=alloy
  ports:
    - name: otlp-http
      port: 4318               # port callers use
      targetPort: otlp-http    # the pod's port with this name

In plain words: "Make an address called alloy-srv. Traffic to port 4318 goes to any pod labelled app: alloy." That's why auth can send traces to http://alloy-srv:4318 without knowing where Alloy is running.

Labels are the glue. The DaemonSet stamps app: alloy on every pod it creates, and the Service's selector looks for that label. Objects find each other by label, not by name.

Watch out: a Kubernetes label (app: alloy) and a Loki label (level, service) are different things with the same name. In this course, "label" alone means a Loki label; for the other we say "k8s label".

3 · What's in alloy.yml, and what to skip

The file holds six objects, separated by ---. You only need to read two of them properly:

ServiceAccount · ClusterRole · ClusterRoleBinding (skip)
Permissions: "Alloy may read pods and their logs." Boilerplate.
ConfigMap (read)
Holds Alloy's config, the inner language. This is where the logic lives.
DaemonSet (skim)
Runs one Alloy on each node. Look at image, ports and resources; skip the rest.
Service (read)
The alloy-srv address you just read.

grafana.yml, loki.yml and tempo.yml follow the same pattern: a ConfigMap (the logic), a Deployment (runs it) and a Service (its address).

4 · The Alloy language: blocks wired together

Alloy config is a set of components. Each component has a type and a name you choose (Alloy docs):

loki.source.kubernetes "pods" {        # type "your-name" {
  targets    = discovery.relabel.pods.output
  forward_to = [loki.process.json.receiver]   # send lines here
}

loki.process "json" {
  forward_to = [loki.write.loki.receiver]
  stage.json { ... }                   # steps applied to each line
}

loki.write "loki" {
  endpoint { url = "http://loki-srv:3100/loki/api/v1/push" }
}

Read forward_to as an arrow. loki.process.json.receiver means "the input of the loki.process component I named json." So the three blocks form a chain:

loki.source.kubernetes "pods" → loki.process "json" → loki.write "loki" → Loki

That chain is the Alloy → Loki part of the pipeline from Lesson 1. To follow any Alloy config, find the first component and keep following forward_to (or output, for traces).

5 · Lab: check it against the live cluster

  1. The DaemonSet made one pod per node:

    kubectl get daemonset alloy

    You should see DESIRED 1, since Docker Desktop has one node.

  2. The Service's selector found that pod:

    kubectl get endpoints alloy-srv
    What does the IP in the output mean?

    It's the Alloy pod's IP. Kubernetes matched selector: app: alloy to the pod's k8s label. If that list were empty, the labels wouldn't match, and traces would have nowhere to go.

  3. Your built-in dictionary. Stuck on any field? Ask the cluster:

    kubectl explain service.spec.selector
kubectl explain daemonset.spec.template

  4. Trace the traces chain yourself. Open alloy.yml and find otelcol.receiver.otlp "default". Follow its output to the end.

    Check your chain

    otelcol.receiver.otlp "default" → otelcol.processor.batch "default" → otelcol.exporter.otlp "tempo" → tempo-srv:4317. You've just read the traces pipeline from ticket 03 on your own.

6 · Check yourself

In a Kubernetes object, what does spec describe?

The desired state. Kubernetes reports the actual state separately, in status.

How does alloy-srv know which pods to send traffic to?

Its selector: app: alloy matches the k8s label the DaemonSet puts on each pod.

In forward_to = [loki.write.loki.receiver], what is the second loki?

It's the name chosen in loki.write "loki" { … }. The server address is the url inside that block.

What does config.alloy: | tell YAML?

Everything indented below it is one text value: Alloy's own config, in its own language.

In short: remember these 3

  1. Two languages: the Kubernetes YAML says what to run; the Alloy config inside the ConfigMap says what Alloy does.
  2. Every k8s object: read kind first, then spec (the state you want). Objects find each other by k8s labels.
  3. Alloy is a chain. Start at the source and follow forward_to / output like arrows.

If you forget everything: read kind, and follow the arrows.

You don't need to memorise RBAC objects, apiVersion, probe settings or volume mounts. When you meet an unfamiliar field, run kubectl explain <kind>.<field>.
