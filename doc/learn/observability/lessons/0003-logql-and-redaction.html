LogQL and redaction

By the end you'll be able to answer a real question ("which logins failed, and why?") with one LogQL query. You'll also be able to say, for any field, whether the logger masks it before it leaves the pod.

Why this exists

Lesson 1 got a log line into Loki. That only helps if you can ask it questions fast, and if it's safe for anyone on the team to look at. Those are the two halves of this lesson: querying (LogQL) and redaction (what the logger hides before a line is ever written).

1 · A LogQL query reads left to right

Every log query has two parts: a stream selector in { }, then an optional pipeline of steps, each starting with | (LogQL: log queries). Each step filters or reshapes the lines coming out of the one before it.

{service="auth-service"}   |= "Login failed"   | json   | reason="wrong_password"
└── 1. which streams ──┘   └ 2. text filter ┘   └ 3 ┘   └──── 4. field filter ───┘
1 · stream selector
Picks streams by label. This is the only part that uses Loki's index, so it's the cheap part. Our labels are only service and level.
2 · line filter
A plain substring (|=, !=) or regex (|~, !~) check on the raw text. Put these early: Loki's docs note that it "only does further processing when a line matches".
3 · parser
| json turns every JSON key in the line into a field you can filter on. Nested keys are flattened with _, so error.name becomes error_name.
4 · label filter
Filters on those fields: =, !=, =~, and for numbers or durations >, >=, <, <=. Combine with and / or.

The one habit: narrow by label first, cut by text second, parse last. The label selector is cheap, a text filter is fast, and | json costs the most because it parses every line that reaches it.

Structured metadata: filtering without parsing

In Lesson 1, Alloy attached trace_id, pod and namespace as structured metadata. That's data stored next to each line, without being indexed or creating a stream (Loki: structured metadata). You can filter on it straight away, without | json:

{service="auth-service"} | trace_id="f88743982cd192ec906042c8d4491502"

This exact query shape is what Grafana runs when you jump from a trace to its logs (Lesson 6).

From lines to numbers

Wrap a log query in a function and it counts instead of listing (LogQL: metric queries). This one answers "how many failed logins per reason in the last hour?":

sum by (reason) (
  count_over_time({service="auth-service"} |= "Login failed" | json [1h])
)

You won't need these often until the dashboards in later tickets, so don't try to learn the syntax now. Just remember that the option exists.

2 · Redaction: masked before it's written

Here's the rule: secrets are removed inside the process, before the line reaches stdout. Alloy, Loki and Grafana never see them. It happens in the logger's pipeline, a chain of Winston formats in logger.ts (createLogger):

const pipeline = [normaliseErrors(), redactSecrets(), applySchema(fixed)];
normaliseErrors
Turns an Error into a plain { name, message, stack }, so the next step can mask the message and stack too.
redactSecrets
Walks the whole entry and masks secrets. The rules are below.
applySchema
Stamps timestamp, service and the rest after redaction, so nothing can mask them.

Redaction has two separate rules. It helps to keep them apart in your head:

Rule A · A secret name hides the whole value

sensitiveKeys.ts decides this. It lowercases the key, strips everything except letters and digits (so x-api-key becomes xapikey), and then checks three lists:

contains
password, secret, authorization, cookie, session, jwt, apikey, signature, and a few more. Example: newPassword.
ends with
token, tokens, pwd, sid. Ends-with, because tokenizer isn't a secret.
exactly
card, cardnumber, cvc, cvv, pan, otp. Exact, because discard and cardinality contain "card".

A match becomes "[REDACTED]", at any depth. { user: { card: {…} } } hides the whole card object.

Rule B · Secret-looking text is masked wherever it appears

Every string, in any field and in the message, goes through maskText.ts:

emails
jane@example.com becomes j***@example.com. The domain is kept, so "every gmail.com send fails" is still visible.
Stripe keys
sk_live_…, rk_test_… and whsec_… become [REDACTED].
query parameters
In /reset-password?token=abc&email=…, the token value is redacted by Rule A's name check, and the email is masked.
Why is the email code so complicated?

The usual one-line "match an email" regex can take exponential time on crafted input like a@a.a.a.a…. That's a ReDoS, and log fields often carry user input, so one malicious signup could freeze a log call. maskText.ts uses only regexes with a single character class, which can't backtrack, and checks the domain in plain code. The comment at the top of the file explains this; there's a test for it too ("masks a hostile email-like string in linear time").

What redaction does not cover: anything that skips the logger. console.log(err) in common/src/middleware/errorHandler.ts (the puzzle from Lesson 1) writes straight to stdout: no masking, no JSON, no trace_id. When you review a PR, any new console.log is a redaction bypass.

The same policy protects traces as well: the span exporter reuses isSensitiveKey and maskText (Lesson 6).

3 · Drill: masked or kept?

Commit to all eight before checking. The field is logged as logger.info('x', { <field>: … }).

Does the whole value become [REDACTED]?

  1. resetToken: "3f9a…"

    Ends with token, so Rule A applies.

  2. tokenizer: "bpe"

    token is an ends-with rule, and this ends with "izer".

  3. "x-api-key": "k_123"

    It's normalised to xapikey, which contains apikey.

  4. cardinality: 12

    card is an exact match rule only.

  5. sessionId: "s-9"

    Contains session.

  6. email: "jane@x.io"

    The name isn't secret, so it's not redacted. Rule B masks the text instead, giving j***@x.io.

  7. card: { number, expiry }

    Exact match on card, so the whole object goes.

  8. reason: "wrong_password"

    Rule A checks the key (reason), not the value. The value only goes through Rule B, which doesn't match it.

4 · Lab: answer real questions

Needs skaffold dev -p observability running and Grafana open (Lesson 1, step 2). In Explore, pick Loki and use Code mode.

  1. Make two kinds of failure. One unknown email, and one wrong password for a user you create:

    curl -sk -X POST https://ecom.dev/api/users/login -H 'content-type: application/json' \
  -d '{"email":"nobody3@example.com","password":"x"}'
curl -sk -X POST https://ecom.dev/api/users/signup -H 'content-type: application/json' \
  -d '{"name":"Lesson Three","email":"lesson3@example.com","password":"Secret#123","passwordConform":"Secret#123"}'
curl -sk -X POST https://ecom.dev/api/users/login -H 'content-type: application/json' \
  -d '{"email":"lesson3@example.com","password":"wrong"}'

    Signup needs passwordConform to match (newUser.ts). If you've run this before, it says the email is in use, which is fine: the user already exists.

  2. Label first, text second.

    {service="auth-service", level="warn"} |= "Login failed"

  3. Parse and filter on a field. Only wrong passwords:

    {service="auth-service"} |= "Login failed" | json | reason="wrong_password"
    Checkpoint: which fields does that line carry, and which are masked?

    reason, userId and email (loginUser.ts). The email shows as l***@example.com. userId is kept, since it's an ID, not a secret, and it's exactly why userId must never be a label (Lesson 1).

  4. Count instead of list. Switch the time picker to "Last 1 hour" and run:

    sum by (reason) (count_over_time({service="auth-service"} |= "Login failed" | json [1h]))

  5. Prove the password never left the pod. Search every auth line for the password you just typed:

    {service=~"auth.*"} |= "Secret#123"
    What should you see, and why the =~?

    Nothing. The request body is never logged, and if it were, password would be redacted. =~"auth.*" is a regex matcher that also covers the unstructured {service="auth"} stream from Lesson 1's puzzle. That stream is the one place a secret could leak, because it bypasses the logger.

5 · Check yourself

Which part of a LogQL query uses Loki's index?

Only the {…} selector, because Loki indexes labels and nothing else. Every | step works through the lines of the streams that selector picked.

Where is a password removed from a log entry?

redactSecrets runs inside createLogger. Nothing downstream ever holds the secret, so a leak can't come from a misconfigured Alloy or Grafana.

Why does applySchema run after redactSecrets?

The code comment says it: "the schema fields are added after redaction so nothing can mask them". Stamping last has a second benefit: a caller's own service or timestamp field can't overwrite the real one.

A PR adds console.log(req.body) to a controller. What's the problem?

Only createLogger redacts. console.log goes straight to stdout, so the body's password would reach Loki in plain text.

From Lesson 1

Which two fields are Loki labels on our log lines?

Only level and service (stage.labels in alloy.yml). trace_id, pod and namespace are structured metadata.

From Lesson 2

In Alloy's config, how do you find where a line goes next?

Components are chained by forward_to (logs) or output (traces). kind and selectors belong to the Kubernetes YAML around it.

In short: remember these 3

  1. LogQL runs left to right: {labels} → |= "text" → | json → | field="x". Narrow cheaply first.
  2. Redaction happens in the logger, before stdout. A secret name hides the whole value; secret-looking text (emails, Stripe keys, ?token=) is masked anywhere.
  3. Anything that skips the logger skips redaction. A new console.log in a PR is a red flag.

If you forget everything: "labels, then text, then json", and "only the logger redacts".

You don't need to memorise the deny-list words, the metric-query syntax or the ReDoS details. They're in the LogQL and redaction sheet.
