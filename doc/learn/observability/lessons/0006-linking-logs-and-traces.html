Lesson 6 · Ticket 03 · ~20 min

Linking logs and traces

By the end you'll have gone from a log line to its trace and back in two clicks. You'll know which three names must match for those clicks to work. And you'll have turned the collector off to see that logins keep working.

Why this exists

Logs say what happened; traces say where the time went. During an incident you need both, for the same request, without copying IDs around by hand. Linking them "natively" is one of the two reasons ADR 0001 picked the Grafana stack. The other half of ticket 03, "the collector being down must never break requests", is what makes all this telemetry safe to run.

1 · Two links, both in Grafana's config

Neither link is code in auth. Both are datasource settings in the ConfigMap at the top of grafana.yml. (Lesson 2: the ConfigMap holds the logic.)

Log → trace: a derived field on Loki

A derived field uses a regex to pull a value out of each log line and turn it into a link (Grafana: Configure Loki):

derivedFields:
  - name: trace_id
    matcherType: regex
    matcherRegex: '"trace_id":"([0-9a-f]{32})"'   # the ( ) part is captured
    datasourceUid: tempo                          # open it in the Tempo datasource
    url: '$${__value.raw}'                        # …using the captured value
    urlDisplayLabel: View trace                   # the button text

In plain words: "in every log line, find "trace_id":"<32 hex>" and add a View trace button that opens that ID in Tempo." You can ignore matcherType. The only part you'd ever change is the regex.

Trace → logs: traces-to-logs on Tempo

tracesToLogsV2:
  datasourceUid: loki
  spanStartTimeShift: '-5m'       # search a bit before the span…
  spanEndTimeShift: '5m'          # …and a bit after it
  tags:
    - key: service.name           # the span's resource attribute
      value: service              # → the Loki label with this name
  customQuery: true
  query: '{$${__tags}} | trace_id="$${__trace.traceId}"'

When you click Logs for this span, Grafana fills in the template. ${__tags} becomes service="auth-service" (from the tag mapping), and ${__trace.traceId} becomes the trace ID. The result is the query you already know from Lesson 3:

{service="auth-service"} | trace_id="f88743982cd192ec906042c8d4491502"

The time shifts are there because a log line and its span "rarely share exact timestamps" (comment in the file; see also Grafana: Trace to logs).

Why $$ everywhere?

Grafana treats $VAR in provisioning files as an environment variable and expands it at startup. $$ escapes that, so $${__value.raw} reaches Grafana as the literal ${__value.raw}, which it then expands per click. Forget a $ and the link silently comes out empty. That's a real review point.

2 · The contract: one name in three places

The trace→logs link only works if a span's service.name exactly equals the Loki service label on its log lines. Grafana's docs warn that if the names don't match, "correlation silently breaks". In our setup the name is written in three places:

the logger
createLogger({ service: 'auth-service' }) writes the JSON service field, which Alloy makes the label.
the bootstrap
startTelemetry({ serviceName: 'auth-service' }) in auth/src/tracing.ts sets service.name.
Grafana
The tags mapping above: service.name → service.

The bootstrap protects this contract on purpose. Its options are applied last, so they win over OTEL_SERVICE_NAME or OTEL_RESOURCE_ATTRIBUTES set in the environment (explicitOptionsDetector in telemetry.ts, pinned by a test). The log→trace link has a contract too: the regex expects compact JSON "trace_id":"…". LOG_FORMAT=pretty in the cluster would break the link and Alloy's labels.

3 · Spans are redacted too, at export

A span attribute can leak a secret just like a log field can. The ?token= of the reset-password link lands in url.query, for example. So every exporter is wrapped in RedactingSpanExporter (spanRedaction.ts), which applies the same policy as the logger: isSensitiveKey on attribute names and maskText on string values, including span events, links and the status message.

why at export time?
One place covers every instrumentation and every custom attribute. And behind the batch processor, the work happens off the request path.
what it doesn't cover
Resource attributes aren't redacted. That's why the bootstrap leaves out the process detector, which "records the full command line, which can carry secrets".

4 · Why a dead collector can't hurt a request

ADR 0001: "Services must keep working with the collector down. Telemetry export is best-effort and must never block a request." Here's how each signal honours that:

logs
Written to stdout (Lesson 1). No network at all on the request path.
spans, inside auth
BatchSpanProcessor puts finished spans in a bounded queue and exports on a timer. If Alloy is unreachable, the export fails after a timeout and the spans are dropped. The request finished long before.
spans, inside Alloy
If Tempo is down, Alloy's exporter queue fills and then drops (comment on otelcol.processor.batch in alloy.yml). Auth only ever talks to Alloy.
no endpoint / tests
A NoopSpanProcessor: nothing is sent, but spans still get IDs, "so logs keep their trace_id and x-trace-id still works locally".

This is pinned by the test 'keeps serving requests when the collector is down' in telemetryExport.test.ts, which points the exporter at a closed port and checks that requests still return 200.

The trade-off, in one sentence: we accept losing telemetry during an outage so that we never lose requests. The opposite, blocking until spans are delivered, would turn an observability outage into a customer outage.

5 · Lab: two clicks, then pull the plug

  1. Log → trace. Log in once (as in Lesson 4). In Explore → Loki, run {service="auth-service"} |= "User logged in", expand the newest line, and click View trace.

  2. Trace → logs. In the trace view, click the root span, then Logs for this span.

    Checkpoint: what query did Grafana write for you?

    {service="auth-service"} | trace_id="…", the tag mapping plus the trace ID. It should show the "User logged in" line (and any others from that request).

  3. Take Alloy away. Alloy is a DaemonSet, so it can't be scaled to zero. Instead, tell it to run only on a node that doesn't exist:

    kubectl patch daemonset alloy -p \
  '{"spec":{"template":{"spec":{"nodeSelector":{"lesson6":"off"}}}}}'
kubectl get pods -l app=alloy        # wait until none are left

  4. Log in during the outage, and time it.

    for i in 1 2 3; do
  curl -sk -o /dev/null -w '%{http_code} %{time_total}s\n' -X POST https://ecom.dev/api/users/login \
    -H 'content-type: application/json' -d '{"email":"lesson3@example.com","password":"Secret#123"}'
done

    Expect three 200s at normal speed. That's the ticket 03 acceptance criterion, seen live.

  5. Bring Alloy back. Undo the patch, restoring the previous template:

    kubectl rollout undo daemonset alloy
kubectl rollout status daemonset alloy

  6. Look for the evidence. Search Loki for the outage logins, and Tempo for their traces.

    What to expect, and what it teaches

    Traces: almost certainly gone. Auth's exporter couldn't reach Alloy and dropped them by design. Logs: the lines were still written to the container's log on the node, so whether they show up depends on whether Alloy picks up where it left off when it restarts. Whatever you find, the lesson is the asymmetry: requests were never affected, and only the telemetry for the outage window may have gaps. Tell me what you saw; it's a good fact to record.

6 · Check yourself

Where is the log → trace link defined?

A derived field in grafana.yml. The logger only writes trace_id into the line, and Grafana turns it into a link when it displays the line.

A PR sets serviceName: 'auth' but the logger keeps 'auth-service'. What breaks?

The link queries {service="auth"}, but the lines are labelled auth-service. It fails silently. Log→trace still works, because it only needs the trace ID.

Alloy is down. What happens to a login's spans?

The batch processor's bounded queue exports off the request path. When exports fail, spans are lost and requests are unaffected.

Why are spans redacted at export rather than when attributes are set?

Instrumentations set attributes in dozens of places we don't control. Wrapping the exporter catches all of them, off the request path.

From Lesson 5

A log line has a trace_id, but Tempo says "trace not found". What's one innocent cause?

IDs exist even for unsampled traces (flags 00). Other innocent causes: the span was dropped during a collector outage, or it's older than Tempo's 72 h retention.

From Lesson 3

Which component masks secrets in log lines?

Only the logger. Spans use the same rules, applied at the exporter.

In short: remember these 3

  1. Both links are Grafana config: a Loki derived field (log → trace) and Tempo traces-to-logs (trace → logs, using {service=…} | trace_id=…).
  2. The links depend on names matching: the logger's service and the span's service.name must be the same string, or trace→logs silently finds nothing.
  3. Telemetry is best-effort: if the collector is down we lose spans, never requests. Spans and logs share one redaction policy.

If you forget everything: "same service name everywhere; drop telemetry, never requests".

You don't need to memorise the datasource keys or the $$ escaping. They're in the traces cheat sheet. Just remember that the links live in grafana.yml.
