Lesson 9 · Ticket 04 · ~20 min

From requests to RED metrics

Your win: explain what auth’s three graphs measure, then follow one latency example to its trace. This lets you review ticket 04 and use it during a slow-login incident.

Based on the current repository, 28 September 2026. The ticket records committed implementation; live dashboard and exemplar acceptance remain unconfirmed. This lab has not been run against a live cluster.

Recall before you read

Why do we keep a trace ID as a log field instead of a Loki label? Say your answer aloud.

Hint, then a refresher if needed

Think about how many different IDs a busy service creates. Each request can introduce a new ID: indexing it as a Loki label creates too many streams. Keep the ID on the log line and filter for it. See Lesson 1. That same cardinality concern will guide our choice of metric labels today.

1 · Three questions about a service

A trace explains one request. A metric describes traffic over time. When login slows down, start with RED: Rate, Errors, Duration. Here these mean:

Rate
How many requests per second reach each route?
Errors
How many 4xx or 5xx responses per second does each route return? That is this dashboard’s definition. A 403 counts even if rejecting an unauthenticated caller is expected.
Duration
How long do requests take? The dashboard shows p50, p95 and p99. p95 estimates the time within which 95% of the observed requests finished.

The error panel’s unit is requests/second, not percent. If 10 requests/sec arrive and 2 requests/sec fail, the error fraction is 20%. The panel plots 2.

These definitions and filters are in grafana-service-detail.yml. A rising error graph is a prompt to investigate the response classes; it does not by itself prove a server failure.

2 · One observation feeds all three

When Express finishes a response, http.ts records its elapsed seconds and final route/status. It excludes /metrics from request metrics so the collector’s scrapes do not inflate application traffic. The histogram is created in metrics.ts:

meter.createHistogram("http.server.request.duration", {
  unit: "s",
  // bucket boundaries are configured here
});

Read this as “keep a distribution of incoming request times, measured in seconds.” Our exporter exposes a classic histogram under http_server_request_duration. Use the names actually in /metrics; the dashboard does not query the dotted OTel name.

A classic histogram exposes three related measurements: _count for observations, _sum for total observed duration, and cumulative _bucket counts. Prometheus: metric types.

# Invented observations: 0.04s, 0.08s, 0.30s
_bucket{le="0.1"} 2
_bucket{le="0.5"} 3
_bucket{le="+Inf"} 3
_count 3
_sum 0.42

Labels and the metric prefix are omitted here to make it readable. le means “less than or equal”: the 0.5-second bucket includes both requests already counted in the 0.1-second bucket. Do not add the buckets together.

Read the dashboard’s PromQL without memorising it 
sum by (route) (
  rate(http_server_request_duration_count{
    service="auth-service", environment="local"
  }[5m])
)

Inside out: select auth’s counts; [5m] selects recent samples; rate calculates their per-second growth, accounting for counter resets; sum by (route) combines matching series while keeping routes separate. Apply rate before aggregation. Prometheus: rate.

The errors query adds status_class=~"4xx|5xx". The duration query uses buckets:

histogram_quantile(0.95,
  sum by (le, route) (
    rate(http_server_request_duration_bucket{
      service="auth-service", environment="local"
    }[5m])
  )
)

Keep le so the calculation retains bucket boundaries. Merge compatible buckets across replicas before estimating p95. Do not average replica p95s. Bucket width limits precision; p95 is an estimate. The actual dashboard uses $__rate_interval in place of a fixed five minutes. Prometheus: histograms and summaries.

Choose a route template

/product/123 and /product/456 should share route="/product/:id". Raw IDs would multiply metric series. Every distinct metric-label combination creates a series. Prometheus: labels.

This bundle reads Express’s matched route at response finish. It groups unmatched requests under unmatched. Its metric labels are service, environment, method, route and status_class. These are project choices; the standard OTel HTTP attribute names differ. OTel HTTP conventions require bounded route templates too.

3 · Follow the numbers to Grafana

  1. Auth records a request. app.ts calls mountObservability(app, { service: 'auth-service' }) before routes.
  2. Alloy pulls /metrics. Pod annotations in auth-depl.yml opt into scraping. Alloy discovers the pod and reads port 3000 every 15 seconds.
  3. Alloy sends the samples. It remote-writes to Prometheus. Grafana queries Prometheus to draw the graphs. See Alloy scrape and remote write.
prometheus.scrape "services" {
  targets = discovery.relabel.metrics.output
  forward_to = [prometheus.remote_write.local.receiver]
  scrape_interval = "15s"
}

Line by line: name the scrape component; give it discovered targets; send results to the remote-write component; repeat every 15 seconds. Ignore discovery internals today. Metrics use scraping here; traces use OTLP.

An exemplar is a bridge to one request

An exemplar attaches an example observation and trace ID to a metric sample. Grafana can draw a dot linking it to Tempo. It is not a trace ID on every metric series. Grafana: exemplars.

Our exemplars.ts adds the latest sampled request’s trace ID to the +Inf bucket in OpenMetrics text. It retains one example per label combination, with a 1,000-entry cap. The dot is an example request, not “the p95 request,” and this implementation does not choose the slowest request.

The chain must preserve it: OpenMetrics scrape → Alloy send_exemplars = true → Prometheus exemplar storage → Grafana’s trace_id destination pointing to tempo. Its span must also reach Tempo. Refresh Lesson 6 if IDs exist but traces are missing.

4 · Practice with immediate feedback

A count rises by 120 across 60 seconds, with no reset. What approximate request rate is that?

120 ÷ 60 = 2 requests/sec. A cumulative count is not itself a rate.

Which value should represent GET /product/123 in the route metric label?

The template groups IDs into a bounded set of routes. Raw paths create extra series.

The Error rate panel shows 2. What does it mean?

This panel counts 4xx and 5xx responses per second. An access log is written at info level, so a 403 need not appear in the error-log panel.

What does clicking an exemplar dot open?

It opens an example trace. Sampling and export failures can still leave the destination missing.

5 · Lab: prove the grouping, then read auth

  1. Run the small local test. From the repository root:

    cd common
npm test -- --runInBand src/observability/__test__/httpMetrics.test.ts
cd ..

    Predict first: two product IDs should produce one route-labelled count of 2. The test also checks secret masking and one access log per request, including the scrape. It passed during lesson creation.

  2. When the cluster is running, forward auth and Grafana. Start your usual skaffold dev -p observability workflow. In separate terminals:

    kubectl port-forward service/auth-srv 3000:3000
kubectl port-forward service/grafana-srv 3001:3000

    Use another available local port if needed and adjust the following URLs.

  3. Create one baseline, then some requests.

    curl -s http://localhost:3000/api/users/currentuser -o /dev/null
curl -s http://localhost:3000/metrics | rg 'http_server_request_duration_count'
for i in 1 2 3 4 5; do
  curl -s -o /dev/null http://localhost:3000/api/users/currentuser
done
curl -s http://localhost:3000/metrics | rg 'http_server_request_duration_count'

    Without a session, this route returns 403. Compare before/after: its 4xx count should grow by at least 5 (other traffic can add more). The route string stays fixed. Repeated metrics scrapes should not increase that application count.

  4. Read the dashboard. Open Service Detail. Choose local and auth-service. Allow at least two scrape intervals. Check request rate, error rate and latency; explain aloud why this 403 traffic raises both rates. No data needs investigation; it does not mean zero errors.

  5. Inspect an exemplar. Look for # {trace_id="…"} on a bucket line in /metrics. If a sampled request produced a dot, click it in the latency panel and compare its trace ID. If there is no dot, check for an exemplar at the source, then scrape/remote-write/storage/link settings. If the dot opens a missing trace, check sampling/export/retention.

Where the rest of ticket 04 fits

The runtime panels read event-loop lag, heap usage and GC duration from metrics.ts. They provide clues; they cannot prove the cause of a slow request. Error logs come from Loki’s level="error" stream. Slow traces come from Tempo: the panel sorts its returned traces over 1 second and takes ten, so it is not proof of the globally slowest ten traces. Remember these three

  1. One duration histogram feeds RED: count growth gives rate, status filtering gives errors, buckets estimate percentiles.
  2. Use route templates: IDs and trace IDs must not multiply metric series.
  3. An exemplar links an example to Tempo: it is not the percentile itself.

Fallback: ask “how many, how many failed, how long?”
