Choose the invariant first

Acceptable overlap
Cache rebuilds and cron work where a duplicate run only repeats tolerable work. A Redis lease can reduce overlap; the write must also tolerate an older worker finishing later.
Unsafe with a lease alone
Money transfers, card charges, stock decrements, exactly-once effects, and cron tasks whose duplicate run corrupts data.
Stock
Use a single conditional update in the system of record. Validate the requested quantity and handle no match. Use durable idempotency separately for repeated events.
const updated = await Product.findOneAndUpdate(
  { _id: id, quantity: { $gte: requested } },
  { $inc: { quantity: -requested } },
  { new: true },
);

Acquire a lease

const token = randomUUID(); // fresh for every attempt/acquisition
const acquired = await redis.set(key, token, { NX: true, PX: ttlMs });
if (acquired !== 'OK') { /* don't perform the protected work */ }

NX and expiry belong to the same command. Bound retries and use backoff with jitter under contention. TTL must cover normal work plus a margin, but no TTL covers an arbitrary pause. A Redis error is not permission to enter a correctness-critical section.

Release: compare and delete atomically

-- KEYS[1]: lease key; ARGV[1]: this acquisition's random token
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
const released = await redis.eval(releaseLua, {
  keys: [key], arguments: [token],
});

1 means removed; 0 means missing or owned by someone else. Never use a plain DEL or separate GET/DEL. This is the Redis 7.x-compatible Lua pattern used by the lab. It protects the key, not a separate store's writes.

Extend: compare and renew atomically

-- KEYS[1]: lease key; ARGV[1]: token; ARGV[2]: positive TTL in ms
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0

Pass a validated positive TTL. Only 1 confirms renewal. On 0, timeout or error, treat ownership as lost; don't start more protected work. Stop renewal when work ends, and bound total renewal time. Renewing cannot undo a stale write already sent to another store, and a paused worker cannot renew.

Fencing: the resource rejects stale writers

Issue a strictly increasing number with each acquisition. Carry it on every write. The store must compare against its last accepted number and mutate the resource atomically. The lab accepts one write per acquisition and rejects numbers less than or equal to the last accepted number.

-- Lab only: acquisition and fence issuance in one atomic turn
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
  return redis.call('INCR', KEYS[2])
end
return 0

KEYS[1] is the lease, KEYS[2] a counter that outlives leases, ARGV[1] the random token and ARGV[2] the TTL. Separate SET then INCR can let an old paused owner obtain a later number. In Cluster these keys need the same hash slot (Lesson 8). A failover can roll back a Redis counter; production fencing requires an issuer whose ordering survives recovery. Every protected write path must enforce fencing. This doesn't provide event deduplication or reject an expired writer before the store has seen a newer fence.
