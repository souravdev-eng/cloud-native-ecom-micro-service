Commands and data types

Only the commands the lessons use so far, each with its time complexity. It grows as lessons are added. The full catalogue is at redis.io.

The rule: unbounded O(N) is an incident

Redis runs commands one at a time, so while one command runs, every other client waits. An O(1) command is fine. A command whose cost grows with the data, such as KEYS, or reading every element of a big collection, stalls the whole server for as long as it takes. Use the bounded version: SCAN instead of KEYS, and UNLINK instead of DEL for big keys.

Strings and counters

A string holds text, a serialised object or a number, up to 512 MB. Lessons 0–1 use only strings.

GET key · O(1)
The value, or nil if the key doesn't exist.
SET key value [EX seconds] [NX] · O(1)
Writes the value. EX sets a time-to-live in the same atomic command; NX writes only if the key doesn't exist yet. node-redis: set(key, value, { EX: 60 }).
INCR key · O(1)
Adds 1 and returns the new value, atomically. A missing key counts as 0. Errors if the value isn't an integer. This is Lesson 0's fix.
INCRBY key n · DECR key · DECRBY key n · O(1)
The same, with a step or downwards. node-redis: incrBy, decr, decrBy.
Why not GET, add, then SET?

Because it's a read-modify-write across two round trips. Another client's command can run in between, and its update gets overwritten: a lost update (Lesson 0). Any single command above is atomic; a sequence of them isn't.

Keys

SCAN cursor MATCH pattern COUNT n · O(1) per call
Walks the keyspace a small batch at a time, so other clients run in between calls. Start with cursor 0 and stop when it returns 0. It can return a key more than once, so make the work idempotent. node-redis: scanIterator({ MATCH, COUNT }).
KEYS pattern · O(N), all keys
Checks every key in one go and blocks the server meanwhile. For debugging only, never in app or lab code.
DEL key … · O(1) per string key
For a key holding a collection, the cost grows with the number of elements, and the server blocks while it frees them.
UNLINK key … · O(1) per key
Removes the keys straight away; a big value's memory is freed later in a background thread, so the server doesn't stall. Prefer it for cleanup and big keys.
FLUSHDB · FLUSHALL
Delete every key in the database, or in all databases. Never in lab code: labs clean up only their own lab:NN:* prefix with SCAN + UNLINK.

Looking inside

PING
Replies PONG. A quick "is it up?" check.
MONITOR
Streams every command the server runs. Great for seeing an interleaving (Lesson 0, step 4); it slows the server down, so use it only in the sandbox and stop it when you're done.

In the sandbox: npm run redis:cli opens redis-cli inside the lab Redis. Add a command after -- to run just that one, e.g. npm run redis:cli -- ping.
