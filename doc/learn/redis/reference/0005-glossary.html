Glossary

Every lesson uses these words with exactly these meanings. Terms are added as lessons introduce them; the lesson that introduces each one is in brackets.

Many processes, one Redis

shared state
Data that several processes read and change. Pods share no memory, so shared state has to live outside them, in Redis or a database. (L0)
worker
One process in a lab, standing in for one pod: its own memory, its own Redis connection. (L0)
round trip
One request to Redis plus its reply. Every command costs one; the network time usually dwarfs Redis's own work. Also called RTT. In Lesson 0's picture, the walk to the keeper and back. (L0)
read-modify-write
Read a value, change it in the app, write it back. Done as two commands, it leaves a gap where other clients can write. (L0)
race condition
A bug where the result depends on how operations from different clients happen to interleave. (L0)
lost update
Two clients read the same value and both write back a change; the second write overwrites the first, which is lost without any error. (L0)
TOCTOU
Time of check to time of use: the gap between reading a value and acting on it, in which someone else can change it. A read-modify-write has one. (L0)

How Redis runs commands

command thread
The single main thread on which Redis executes every command, one at a time. Other threads only do side work, such as freeing memory or reading and writing sockets. In Lesson 0's picture, it's the keeper of the whiteboard. (L0)
atomic
No other client's command can run in the middle of it. Every single Redis command is atomic; a sequence of commands is not. (L0)
pipelining
Sending several commands without waiting for each reply. Saves round trips; not atomic. (L0)

Caching

system of record
The store that holds the real, authoritative data. For products, MongoDB. A cache is never one. (L1)
derived copy
Data made from the system of record that can be thrown away and rebuilt at any time. Every cached value is one. (L1)
cache hit · cache miss
The key was in the cache, so the copy was used · the key wasn't there, so the app had to read the system of record. (L1)
cache-aside
The app looks in the cache; on a miss it reads the system of record and stores a copy itself. The cache never fetches anything. Also called lazy loading. In Lesson 1's picture: check the whiteboard, else walk to the filing room and pin up a photocopy. (L1)
TTL
Time to live: the seconds a key has left before Redis deletes it. Set with EX on SET, read with the TTL command. In Lesson 1's picture, the throw-away time on a photocopy. (L1)
cache key
The name a cached value is stored under. It must cover everything that can change the answer. (L1)
key prefix
The fixed start of a key saying what kind of thing it holds, such as product:. In the labs, lab:NN:. (L0, L1)
versioned key
A key prefix with a version in it (product_search:v2:), changed when the meaning of the keys changes so old copies are never read again. (L1)
stale
A cached copy that no longer matches the system of record. (L1)
cache invalidation
Making a cached copy stop being used after the original changes: deleting it, or making its key unreachable. (L2)
invalidate on write
Doing the invalidation as part of every write to the system of record, rather than waiting for the TTL. (L2)
delete vs update on write
On a change, delete the copy (the next read fetches it) or write the new value into the cache. Delete is the default: two overlapping updates can land in the wrong order. (L2)
delete after commit
Invalidate only after the database write has succeeded, so no reader can re-cache the old value in between. (L2)
stale set
A race: a reader loads a value before a change and saves its copy after the invalidation, putting the old value back. In Lesson 2's picture, the colleague walking back with an old photocopy. (L2)
backstop TTL
The TTL's job once you invalidate on write: the longest a copy can stay wrong when an invalidation is missed or beaten by a stale set. (L2)
generation counter
A counter that is part of every key in a family; INCR it and the whole family is invalidated at once, without finding the keys. In Lesson 2's picture, the edition number at the top of the board. (L2)

Keeping cache misses from multiplying work

cache stampede
Many misses for the same answer start overlapping expensive loads. (L3)
single-flight
One pending load per key inside one process; other requests share its result. Also called request coalescing. Not one load per cluster. (L3)
TTL jitter
Varying expiry times so many keys don't all expire together. (L3)
negative caching
Keeping a successful “nothing found” answer briefly, so repeated empty queries don't all read the store again. (L3)
soft TTL
A freshness deadline after which an acceptable older copy may be served during refresh, until a hard expiry deadline. (L3)

When the cache fails

fail open
Continue an operation when a dependency fails; for an optional cache, fall back to the system of record. (L4)
fail closed
Refuse or delay an operation when its required dependency cannot be used. (L4)
command timeout
A deadline on waiting for one command's answer. It doesn't expire a key, connect a socket, or guarantee cancellation of the command. (L4)
reconnect strategy
The client's policy for retrying a broken connection. It doesn't give requests a deadline. (L4)
readiness
Whether a pod can serve traffic according to its required-dependency contract. (L4)

Coordination

lease
Temporary ownership that expires. Expiry allows a new owner but doesn't stop an old process writing. (L5)
ownership token
A unique random value for one acquisition; compare it atomically when releasing or renewing the lease. (L5)
fencing token
A strictly increasing acquisition number carried to a store that atomically rejects stale numbers when writing. (L5)
atomic conditional update
One store operation checks its predicate and applies its change together, such as subtracting stock only if enough remains. (L5)

The labs

sandbox Redis
The local Docker Redis from sandbox/redis-learning/docker-compose.yml, on host ports 6390–6399. The only Redis lab code may connect to. (L0)
connection guard
connect() in the lab helpers: it throws for any URL that isn't the sandbox Redis, with no override. (L0)
lab prefix
lab:NN:, the key prefix each lab writes under and the only thing its cleanup deletes. (L0)
barrier
A lab helper that holds each worker at a point until all of them arrive, to force the worst-case timing on every run. (L0)
pause point
A lab helper (createPauses) that holds one worker at a named step until another worker has done its part and resumes it, to force one exact order of events. (L2)
slow store
A lab helper (createSlowStore) standing in for the system of record: every read and write waits a set latency, and reads are counted. (L2)
broken / fixed variant
The two versions of each lab: one shows the failure, one shows the fix against the same scenario. --check runs both and asserts the outcome. (L0)
