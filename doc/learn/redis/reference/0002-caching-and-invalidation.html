Caching and invalidation

The caching patterns and defaults the lessons use, for lookup after the course. It grows as lessons are added: invalidation came with Lesson 2, stampede protection with Lesson 3, and what to do when Redis is down with Lesson 4.

The rule: the cache is a copy

A cached value is derived from the system of record (for products, MongoDB) and can be thrown away and rebuilt at any time. Never store anything in a cache that exists nowhere else. Every cached value needs a TTL, which limits how long a wrong copy can survive.

Cache-aside

The pattern product uses (Lesson 1). On every read:

  1. Look: GET key. If it returns a value, that's a hit: answer with it.
  2. Fetch: on a miss, read the system of record.
  3. Store: SET key value EX ttl, in one command, then answer.
const cached = await redis.get(key);
if (cached !== null) return JSON.parse(cached);
const fresh = await loadFromDb();
await redis.set(key, JSON.stringify(fresh), { EX: ttlSeconds });
return fresh;
Good for
read-heavy data where a short delay before changes show up is acceptable. Only data someone asked for is cached, so the cache stays small.
Costs
every miss pays for a Redis round trip plus the database read. A copy can be stale until it's invalidated or expires (see Invalidation below). Many pods missing the same key at once all hit the database (Lesson 3).
Who does the work
the app. Redis never fetches anything and doesn't know the database exists.

Choosing a pattern

cache-aside (lazy loading)
the default. The app fills the cache on a miss. Used by product.
write-through
the app also writes the new value to the cache every time it writes the database. Fewer stale reads and misses; caches data nobody may read. Usually combined with cache-aside for misses.
read-through
like cache-aside, but a caching library does the fetch on a miss, so the app only talks to the cache. Not used in this repo.
write-behind
the app writes only to the cache and something copies it to the database later. The cache becomes the only copy for a while, which breaks the rule above. Out of scope for this course.

Key design

Prefix every key
with what it holds: product:, product_search:v2:. Prefixes make keys readable in MONITOR and let you find a family with SCAN … MATCH product:*.
The key is the whole question
anything that can change the answer must be in the key. Leave a filter out and two different questions share one answer (Lesson 1's old quantity bug).
Normalise before hashing
sort object fields so the same question in a different order gives the same key.
Hash long questions
MD5 (or any stable hash) of the normalised query gives a fixed-length key. It's a name, not a security measure.
Version the prefix
bump it (v2, v3) when the key's meaning or the value's shape changes, so no pod reads copies made under the old rules. The old keys expire on their own.

the product detail page. The cache wrapper's default, product/src/cache/redisCache.ts.

a text search, the most expensive query. product/src/routes/showProduct.ts.
product_search:v2:<md5> otherwise · 10 min (600 s)
category and filter lists, first page only.
not cached
empty results, a missing product, plain listings with no filter, later pages of a category or filter list.

Choosing a TTL

Ask: how long may a user see the old value after a change, and how expensive is a miss? A longer TTL means fewer database reads and a longer window for stale data. If changes are invalidated on write (see Invalidation below), the TTL is only the backstop for invalidations that were missed.

  • Always set it in the same command: SET key value EX ttl, never SET then EXPIRE.
  • TTL key returns the seconds left, -1 for a key with no expiry (a bug in a cache), -2 for no such key.

Invalidation

What to do when the system of record changes (Lesson 2). Every change must make every affected copy stop being used, or the copy stays wrong until its TTL.

Delete, don't update

On a write, delete the cached copy and let the next read fetch the new value. Writing the new value into the cache instead (write-through) breaks when two writes to one key overlap: their SETs can land in the other order, and the cache keeps the older value. Two deletes can't be in the wrong order.

Delete after commit

Invalidate only after the database write has succeeded. Delete first, and a reader can load and re-cache the old value in the gap.

/** 1. Commit. */
await product.save();
/** 2. Then invalidate. */
await redis.del(`product:${id}`);

The stale set, and the backstop

Even a correct delete can be beaten: a reader loads the old value before the write, and saves it after the delete. Nothing deletes it again. The TTL is the backstop that bounds how long it survives. So, once you invalidate on write, choose the TTL as "the longest a missed invalidation may last", not "how often to refresh".

Invalidating a family of keys at once

When the keys can't be found from the change (search results: a key is a fingerprint of a query, not a list of products), use a generation counter:

/** Read: a missing counter reads as 0. */
const gen = Number(await redis.get('product_search:gen'));
const key = `product_search:v2:g${gen}:${md5(sortedQuery)}`;

/** Write, after the database commit. */
await redis.incr('product_search:gen');
  • Read the counter before loading from the database; bump it after the commit. Either order swapped lets an old value in under the new number.
  • Old copies are never read again and expire on their own. Costs: one extra round trip per read, and every bump invalidates the whole family, including copies that were still right.
  • A per-item counter (product:gen:<id>) also defeats the stale set for one key, as lab 02's fixed variant shows.
  • A versioned prefix (v2) is the same idea, bumped by hand in code when the key format changes.

Options for "invalidate all searches"

generation counter
one INCR, O(1), race-safe. The default.
SCAN MATCH + UNLINK
walks the keyspace on every write; still loses to the stale set. Never KEYS, which blocks Redis.
reverse index (a set of search keys per product)
precise, but every cached search writes to many sets, which can themselves go stale.
shorter TTL only
a stopgap: fewer minutes wrong, more database reads.

Stampede mitigation layers

Lesson 3 shows 200 misses becoming 200 loads, then 4 loads with single-flight across four worker processes. Combine layers according to the work you need to limit:

One hot key: single-flight
Keep one pending promise per complete cache key in a process-wide map. Other requests await it. Clear it on success and failure. One load per process, not per cluster; requests still need bounded waits and error handling.
Many keys: TTL jitter
Randomise each fill's TTL to spread expiry deadlines. For a maximum stale budget of 60 seconds, use 50–60 seconds, not 60–70. Jitter doesn't prevent simultaneous misses on one hot key.
Repeated empty queries: negative caching
Cache a successful empty response briefly (e.g. 15 seconds), under the complete query key. Never convert a store error into absence. Invalidate on creation or accept the delay; limit distinct keys. Product currently skips empty results.
Too much work across pods: a rebuild lease
Coordination can further reduce duplicate loads. Waiters need a bounded wait or an acceptable old copy; the holder can outlive its lease. Lesson 5 covers these limits. Don't use a cache-rebuild lease as an inventory correctness guarantee.
Acceptable older copies: soft TTL
A freshness deadline triggers a coordinated refresh while readers use the old copy until a hard deadline. Define the tolerated stale window.
Early refresh of a hot key: XFetch
Probabilistic refresh before expiry, weighted by rebuild duration and time remaining. Further reading in Resources, not required for the lab.
// Budget: stale copies live at most 60 seconds.
const ttlSeconds = 50 + Math.floor(Math.random() * 11);
await redis.set(key, JSON.stringify(answer), { EX: ttlSeconds });
