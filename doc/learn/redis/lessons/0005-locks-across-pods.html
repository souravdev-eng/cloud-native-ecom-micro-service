Lesson 5 · Day 2 · ~25–30 min · local lab

Who gets the last Kindle?

Lesson 4 let a request carry on when an optional cache failed. Stock needs a stronger rule: two shoppers cannot both buy the last unit. We'll try a Redis lock, stop its owner, and finish with the simpler answer our product listener already uses.

Before you start

Recall check: Lesson 4 in 2 minutes

From memory: why should a cache have a deadline? Does a timed-out command necessarily stop running? When should an operation refuse to continue?

Hint: a copy is optional; the real stock count isn't.

Show the answers

A deadline bounds how long a request waits for the cache. It doesn't prove cancellation. Carry on from the store when an optional cache fails; refuse or delay when a required correctness check cannot be made. Revisit Lesson 4's recap if needed.

By the end, you can explain why a lock with a TTL can allow two writes, distinguish an ownership token from a fencing token, and choose one conditional database update for stock.

Your lab setup

two Node workers

one fake stock store

npm install

How the lab forces timing and cleans up

Run one copy of lab 05 at a time. All Redis keys live under lab:05:*. The parent gates worker requests so the broken race happens every time. In the pause experiment it sends SIGSTOP, confirms the OS reports the worker stopped, waits more than its entire 800 ms TTL, and checks Redis has expired the key. Only then can the second worker start.

On success, failure, a 20-second worker deadline, or handled SIGINT/SIGTERM, cleanup kills any remaining workers, waits for their close events, and scans/unlinks just this prefix. A forced kill of the parent or host loss cannot run its cleanup; avoid killing the parent with SIGKILL during this experiment. SIGCONT resumes a stopped process; SIGKILL can terminate one.

1 · The question: one left on the shelf

Imagine a checkout promotion in our shop. This checkout race is made up for the lab; the quantity listener we'll read later is real.

Stock says one Kindle remains. Pod A reads one. Before it saves its change, pod B also reads one. Each promises a shopper a unit and saves zero. Redis might handle every command correctly and the shop can still sell two units.

2 · Predict

A pod holds a Redis key with a TTL, then freezes for longer than the TTL. Can it still write when it resumes?

Expiry removes a Redis key. It doesn't stop another process or revoke a request already headed to a different store.

3 · See it break

  1. Let both workers read the last unit.

    npm run lab:05 -- --broken

A: no protection
  accepted purchases: 2 ✗
  oversold:          1 ✗
  double write:      yes ✗
  remaining stock:   0

    The stored count isn't negative. Both wrote zero using an old read. Count accepted purchases as well as the final value: two promises against one unit is an oversell.

4 · Slow motion: borrow the key

Picture a stock clerk accepting changes to the shelf count. Two colleagues try to act on the same old count. Put a temporary permission slip on Redis's whiteboard: only its owner should ask the clerk to write. The keeper issues it to one colleague at a time, with an expiry time.

permission slip
a Redis key set only when absent, with a TTL.
signature
a random value unique to this acquisition; release must match it.
stock clerk
the system of record, a separate component that must enforce its own write rules.

This helps while the first colleague finishes before the slip expires. It doesn't stop someone who fell asleep and wakes up with old instructions.

5 · Fix it, then break the fix

  1. Serialize the happy path.

    npm run lab:05 -- --lock

    Expect one accepted purchase, zero oversold, and no double write. A gets the slip; B is forced to try and be refused. A writes zero and releases. B acquires, reads zero and cannot buy.

const token = randomUUID();
const acquired = await redis.set(key, token, { NX: true, PX: 10000 });
// Only proceed if acquired is "OK".
// Read stock and write while the lease is valid.
// Release with a token-checked Lua script, never a plain DEL.

NX makes acquisition conditional on absence. PX gives the TTL in milliseconds in the same command; a later expiry command could be skipped by a crash. Generate a fresh random token for every acquisition.

Release must compare and delete in one Lua script. A separate GET followed by DEL has another gap: the old lease could expire and a new owner could acquire between them. See the release script.

  1. Freeze the owner beyond expiry.

    npm run lab:05 -- --paused

    Expect a PID and a confirmed SIGSTOP lasting over 800 ms, then two accepted purchases, one oversold, and double write: yes. A read one and stopped. Its slip expired. B acquired a new slip, read one and wrote zero. A resumed and wrote its old zero too.

    The old token's release returns zero while B still owns the key. That's correct: A cannot delete B's slip. It did nothing to prevent A's stock write. A real pod can pause during garbage collection, host suspension or scheduling; it doesn't need to receive SIGSTOP.

Increasing the TTL only changes how long a pause must last. Renewal can reduce ordinary expiry, but a stopped worker cannot renew. Checking the key immediately before a write still leaves a gap between that check and the store's write.

Put a number on the permission slip

The clerk can remember the newest permission number it accepted. A carries number 1. B gets number 2 and writes. When A returns with 1, the clerk refuses the old request. The check and write must happen atomically inside the store; a check in the application leaves the same gap again.

  1. Repeat the same pause with numbered writes.

    npm run lab:05 -- --fenced

    Expect one accepted purchase, no double write, and one stale write rejected. The lab issues the number in the same Redis Lua script as acquiring the key, then sends it with the write. The independent store accepts only a number greater than its last accepted number, and updates that remembered number together with stock.

A random ownership token proves “this key is still mine”; it has no order. An increasing number lets the store reject an older owner once it has accepted a newer one. Fencing doesn't automatically deduplicate repeated orders, or reject an expired owner before a newer number reaches the store.

Limits of this teaching fence

The lab permits one write per acquisition, so equal numbers are rejected too. Multi-write designs need an explicit rule for repeated operations under one fence. The Redis counter is sufficient for this single-node experiment, but it can roll back with lost writes on failover. A real fence issuer must guarantee numbers never go backwards across recovery, and every path into the protected store must enforce them. Lesson 7 returns to lost writes. Deleting the lab counter during cleanup is safe only because its fake store is also discarded.

For stock, give the whole instruction to the clerk

  1. Remove the lock and make one conditional decrement.

    npm run lab:05 -- --atomic
# --fixed is an alias for --atomic

    Expect one purchase and zero oversold. Each worker asks “decrement one only if at least one remains”. The store checks and changes in one turn. The second request sees the first request's result, even if either worker paused before sending it. No lease, renewal, release or fencing service is needed.

  2. Verify every step.

    npm run lab:05 -- --check
npm run labs:verify

    The check requires purchase counts 2, 1, 2, 1, 1; final stock zero; a confirmed pause beyond TTL in both paused runs; rejection of the old fence; token-safe release while the newer lease exists; and worker/key cleanup. The full verifier repeats every local lab three times.

This puts the invariant next to the real data and makes fewer components responsible for correctness. It protects stock against competing requests. Repeated delivery of the same order is a separate problem: validate positive quantities and use a durable order/event identity so retries cannot decrement again.

6 · Now name it

lease
temporary ownership that expires. A Redis “lock” with a TTL is a lease, not indefinite exclusion of all writes.
ownership token
a unique random value used to release or renew only the acquisition you own.
fencing token
a strictly increasing acquisition number carried to a store that atomically rejects stale numbers when writing.
atomic conditional update
one store operation checks its predicate and applies the change together.

Use a Redis lease for a cache rebuild or a cron single-runner where occasional overlap merely repeats acceptable work. A cron task charging cards needs correctness protection at the payment boundary. Money and stock must not depend solely on a Redis lease. Use store constraints, atomic updates, transactions where needed, and durable idempotency.

Redlock acquires a majority of independent Redis primaries within a bounded time window. Its safety depends on timing assumptions and the protected resource; a quorum doesn't cancel a paused process's later write. Read Kleppmann's critique and antirez's response together before adopting it. This lesson's inventory solution stays a conditional database update.

7 · In our repo: stock changes on order events

From product/src/queues/listeners/productQuantityUpdate.ts:

const updated = await Product.findOneAndUpdate(
  { _id: data.id, quantity: { $gte: data.quantity } },
  { $inc: { quantity: -data.quantity } },
  { new: true },
);
findOneAndUpdate
one MongoDB operation on the product document, already used by the event listener.
_id
selects the product named in the quantity event.
quantity: $gte
matches only when enough stock remains for the requested decrement.
$inc
subtracts from the current stored quantity, rather than saving a count read earlier.
new: true
returns the updated document. No match yields null.

The listener distinguishes missing products from insufficient stock, acknowledges either case and returns. On success it deletes product:${data.id} and acknowledges the message. The source notes the order is already committed upstream; compensation remains future saga work. Preventing a negative stock count here does not make the whole checkout transaction atomic or deduplicate redelivered events.

Recall Lesson 2: deleting the detail key still leaves cached search lists stale. Stock correctness and cache freshness are separate rules. This lesson changes no product code.

In short: remember these 3

  1. A TTL gives temporary permission. Expiry lets a new owner start; the old process can still write.
  2. Protect both boundaries. Token-checked release protects the Redis key; fencing checked inside the store rejects an older writer after a newer one.
  3. Ask the store to enforce stock. One conditional decrement beats a lease for this invariant; event retries still need idempotency.

If you forget everything: tell the stock clerk “subtract only if enough remains” in one instruction.

You don't need to memorise Lua syntax or Redlock's timing maths. Keep the locks sheet nearby.

8 · Check yourself

Why must release compare the token and delete in one script?

Expiry and reacquisition can happen between separate commands. Atomic compare/delete protects ownership of the key only.

A writes with fence 7 after the store accepted fence 8. Where must rejection happen?

The protected resource must reject stale requests atomically; an application check leaves another gap.

What's the simplest stock protection for one product document?

The database checks enough stock and changes it in one operation, with no lease-expiry gap.

Which cron job is a reasonable use of a Redis lease alone?

Judge the consequences of overlap, not the label “cron”. Financial effects and deduplication need durable protection.
