Lesson 4 · Day 2 · ~25–30 min · local + live lab

When the whiteboard stops answering

Lesson 3 kept a crowd of cache misses from overwhelming MongoDB. Now ask what our product pods do when Redis itself stops answering. Products still exist in MongoDB; a slow cache shouldn't stop shoppers seeing them.

Before you start

Recall check: Lesson 3 in 2 minutes

From memory: what does sharing a pending fetch protect? How many loads remain across four pods? What does varying the TTL protect?

Hint: one note on each team's desk, and many different copies coming down together.

Show the answers

Single-flight shares one load per key inside one process. Four pods can still load four times. TTL jitter spreads different keys' expiry times; it doesn't combine reads of one hot key. Revisit Lesson 3's recap if needed.

By the end, you can give a cache request a waiting budget, choose whether to continue when a dependency fails, and separate an observed outage from a prediction made by reading code.

What the lab sets up and cleans up

The lab saves lab:04:cache:kindle through the direct connection. It creates a proxy through the API, connects through it, then adds a downstream latency toxic: two seconds on replies, with no random variation. Connection setup isn't part of the measured requests.

Both versions use the same delayed path. On completion or a caught error, the lab disconnects the proxy client, deletes its proxy (including the toxic), and scans/unlinks only lab:04:*. It never clears the database. Run only one copy of lab 04 at a time. After a forced process kill, npm run redis:down removes the leftover proxy environment; start it again before retrying.

1 · The question: the cache is still there

Imagine the Kindle page normally returning a saved price quickly. Then the network to Redis slows down. The cached copy exists, but the product pod waits two seconds for the keeper to reply. Every shopper using that path pays the delay.

This incident is made up for the local lab. Our real routes also await Redis, so we'll inspect their behavior and give you a separate live experiment. If three product pods share the same slow Redis, adding pods doesn't shorten that wait. How long should each pod wait before fetching the original?

2 · Predict

Redis replies after 2 seconds. The client has a connection timeout but no command deadline. How fast is an established connection's GET?

A connection timeout limits establishing a socket. It doesn't limit commands sent through an already connected socket. Redis doesn't fetch from MongoDB.

3 · See it break

  1. Make replies slow.

    npm run lab:04 -- --broken

Broken: wait for every cache reply
  injected delay:    2000 ms (replies only)
  command deadline:  none
  request 1:         2002 ms · cache · price 149
  request 2:         2004 ms · cache · price 149
  request 3:         2004 ms · cache · price 149
  store loads:       0

    These are measured local results; your milliseconds will vary. The answer is correct, but every request is slow. A live service could accumulate waiting requests while the cache remains connected.

4 · Slow motion

  1. The pod sends GET. Redis has the price and generates a reply.
  2. The relay holds that reply for two seconds. The socket stays connected.
  3. The route awaits the promise, so it doesn't read the store or send an HTTP response yet.

An error event listener reports socket problems. It doesn't make the route take another path, and a slow but working socket may produce no error at all.

5 · Why: put a limit on the walk

Reuse the whiteboard picture. The product pod walks to the keeper for a photocopy, but the keeper doesn't answer promptly. The original is still in the filing room. Give the pod a rule: “Wait briefly for the copy; if that fails, go to the original.”

The waiting budget is the command deadline. The filing room is MongoDB. Continuing with the original is the fallback. The copy is an optimization, so its failure shouldn't become a failure of the original.

That rule suits product reads. A security decision or a coordination lease needs its own failure policy: continuing without the required check may be wrong. Choose the policy from what the dependency protects.

6 · Fix it: stop waiting for the copy

  1. Run the same delay with a waiting budget.

    npm run lab:04 -- --fixed

Fixed: stop waiting, read the store
  injected delay:    2000 ms (replies only)
  command deadline:  100 ms
  request 1:         123 ms · fallback · price 149
  request 2:         121 ms · fallback · price 149
  request 3:         122 ms · fallback · price 149
  store loads:       3

    After about 100 ms without a cache answer, each request reads the 20 ms fake store. It returns 149 without waiting to write a new cache copy. A real response budget includes both the cache wait and the database read, plus scheduling and network time. Choose those budgets from the service's latency target; 100 ms is a teaching value.

  2. Check both outcomes and cleanup.

    npm run lab:04 -- --check
npm run labs:verify

    The check requires all three broken requests to wait at least two seconds, all three fixed requests to finish below 500 ms (100 ms cache budget + 20 ms store delay + scheduling allowance), the expected answer and source, three fixed store loads and zero broken loads. It also checks that lab keys and the proxy are gone. The verifier includes this lab and runs each check three times.

A timeout ends the wait; it doesn't undo a command

The lab races redis.get(key) against a timer and clears that timer in finally. Node-redis 4.7.1 does not give this in-flight GET a deadline merely because the socket has a connectTimeout. A late read can still finish. The lab handles its eventual promise settlement and disconnects the dedicated client at the end, discarding the three outstanding reads; it doesn't queue QUIT behind them.

In production, bound pending commands, disable or cap offline queuing, and bypass a repeatedly failing cache for a short recovery interval. Reconnect with bounded backoff and jitter so pods don't all retry together. Avoid disconnecting a shared client for every request timeout: that can disturb other requests. Never treat a timed-out write or lock acquisition as proof that Redis didn't execute it.

Fallback increases database work. Keep Lesson 3's single-flight, database concurrency limits and overload policy; a healthy MongoDB under one request isn't proof it can absorb all cache traffic. Put a deadline on the store read too, and report cache degradation separately from successful HTTP responses.

7 · Now name it

See also the glossary.

fail open
continue the operation when a dependency fails. For this optional cache, read MongoDB instead.
fail closed
refuse or delay the operation when its required dependency cannot be used. This can suit security checks; it hurts availability if imposed by an optional product cache.
command timeout
a deadline on waiting for one command's answer, distinct from connecting a socket or expiring a key.
reconnect strategy
the client's policy for trying a broken connection again. Recovery of the connection doesn't impose a request deadline.
readiness
whether this pod can currently serve traffic according to its dependency contract.

The observability work's health contract makes /healthz a process check without dependency calls. /readyz runs named checks with deadlines (default one second); any error or timeout returns 503. Those deadlines bound the probe response, not cancellation of its dependency calls.

If MongoDB can serve product reads while Redis is unavailable, mark cache health as degraded in metrics/logs rather than removing every product pod from traffic. Required stores belong in readiness. This is a proposed contract for product: product's current app doesn't mount these health routes. Don't claim that a readiness probe already protects it.

8 · In our repo: inspect, then measure

From product/src/redisClient.ts:

const connectRedis = async (url: string) => {
  client = createClient({ url });
  client.on("connect", () => {
    console.log("Redis Server connected");
  });
  client.on("error", (err) => {
    console.error("Redis error:", err);
  });
  await client.connect();
};
createClient({ url })
no explicit reconnect policy, no command deadline, no explicit offline queue limit. “No configured strategy” does not mean “no reconnect”: node-redis 4.x supplies a default retry policy.
connect event
logs a socket connection attempt's success. Verify readiness with a successful command; this message alone isn't proof that product endpoints recovered.
error listener
logs Redis errors; it doesn't catch the rejected promise inside a route or provide a fallback.
await client.connect()
startup awaits this before Elasticsearch setup and app.listen. Default retries can keep startup waiting; if connect rejects, the startup wrapper exits. Exact outage timing remains to be measured.

The detail route in showProductDetailById.ts:

const cachedProduct = await cache.get(redisKey);
if (cachedProduct !== null) {
  res.status(200).send(cachedProduct);
} else {
  const product = await Product.findById(req.params.id);
  // ... not-found check ...
  await cache.set(redisKey, product);
  res.status(200).send(product);
}

The initial GET sits before MongoDB and has no cache-specific catch. Only a successful miss takes the database path. Even after a database read, the SET is awaited before the response. Both waits can prevent a successful response. showProduct.ts similarly awaits GET and SET for eligible cached queries, without a Redis fallback. A query excluded by shouldCache skips those cache calls. The exact HTTP error, waiting time and recovery behavior need live evidence.

The deployment in k8s/product-redis-depl.yml:

metadata:
  name: product-redis-deployment
spec:
  replicas: 1
  # ... selector ...
  template:
    spec:
      containers:
        - name: product-redis
          image: redis:alpine

The name identifies the deployment to scale. One replica means scaling to zero removes the only cache server; this isn't a failover exercise. The outer spec configures the deployment; template describes its pods, and the inner spec.containers lists the programs each pod runs. The container name labels that program; image selects its Redis build. It is unpinned, unlike the local lab's Redis 7.4.11. Ignore the omitted selector and pod labels here; they connect the deployment to its pods. The omitted manifest mounts a PVC; don't predict an empty cache merely from replacing a pod.

Assessment: the current request and startup paths don't make Redis optional. That isn't acceptable for an optional product-read cache. A follow-up should bound GET waits, catch cache-specific failures and read MongoDB, make cache fills best-effort within a budget, bound pending work and reconnects, and allow startup in a recorded degraded state when required stores are healthy. Keep genuine MongoDB errors visible. This lesson changes no product code.

Live lab: record what the platform really does

Evidence boundary

The author did not run this outage experiment against skaffold dev. No live status codes, latency or reconnect timings are asserted here. The source findings above and the local results are verified; see NOTES.md. Use the following experiment to fill the gap.

  1. Use the local development cluster and an authenticated baseline.

    Run skaffold dev -p minimal from the repo root in another terminal if your local build/push setup supports it. Lesson 1's setup explains the repo's local.push: true and the no-push build/deploy alternative. Record which mode you use; a build/deploy run isn't a skaffold-dev observation. Use the login cookie and an existing product ID from Lesson 1. The script deliberately accepts only the docker-desktop context.

    kubectl logs -f deployment/product-deployment --all-containers=true --since=1m

    Keep this log stream in another terminal to watch disconnect errors and connection messages. Both baseline endpoints must return 200. A 403 means authentication failed; it isn't evidence about Redis.

  2. Take Redis down, measure, and restore it in one script.

    cd sandbox/redis-learning
export COOKIE_JAR=/path/to/your/cookies.txt
export PRODUCT_ID=your_existing_24_character_product_id
bash labs/04-redis-down-or-slow/live.sh

    The script calls detail and ?search=kindle before the outage, scales product-redis-deployment to zero, waits for its pod to disappear, calls both endpoints again, then scales back to one replica and repeats the requests. Every curl prints HTTP status, elapsed seconds and exit code. Curl stops waiting after ten seconds; exit 28 means the measurement timed out, not that the server has a ten-second timeout.

    It installs an exit trap before scaling down. Normal completion, command errors, Ctrl-C and TERM all attempt restoration to one replica and wait for rollout. If restoration itself fails it prints the failure. SIGKILL or loss of the terminal/host can't execute that trap. Manual recovery:

    kubectl --context docker-desktop -n default scale deployment product-redis-deployment --replicas=1
kubectl --context docker-desktop -n default rollout status deployment/product-redis-deployment --timeout=120s

    Use your namespace if you set NAMESPACE. Do not leave Redis at zero. Don't edit manifests while measuring: a skaffold redeploy could restore the replica during the outage.

  3. Write down the result before deciding.

    For detail and search, record baseline status/time, outage status/time, curl exit code and the first successful response after restoration. Copy relevant Redis error/connect messages and say whether an HTTP response actually recovered. If recovery is delayed, repeat the bounded curls; don't call a connection log alone recovery. Record environment, client version, whether the route was cache-eligible, and whether you saw an error, a wait, or a database fallback.

    Add this evidence to a learning record or NOTES.md. Startup blocking is a source finding here; this script leaves product running and doesn't test a fresh product startup. Don't turn that prediction into a measured claim.

In short: remember these 3

  1. A copy should be optional. Cache failure should lead to the original when the original can safely serve the request.
  2. Limit how long you wait. A command deadline is separate from connection setup, retries and key TTL. A timeout doesn't undo an in-flight operation.
  3. Measure failure and recovery. Read the route, record its HTTP result and time, restore Redis to one replica, then verify successful responses.

If you forget everything: if the keeper doesn't answer promptly, fetch the original within the request's budget.

You don't need to memorise Toxiproxy's JSON or one hundred milliseconds. Remember the dependency's purpose and choose a measured waiting budget.

9 · Check yourself

What makes the fixed read fast despite a slow cache?

TTL expires data. Reconnect restores a socket. Neither bounds an established connection's command wait.

The GET timed out locally. What can you conclude?

A response timeout isn't cancellation or evidence of absence. This matters even more for writes and lock acquisition.

An optional cache fails, but the database can serve the traffic. What readiness contract fits?

Readiness follows required dependencies. Liveness shouldn't depend on a cache. The fallback must be verified and capacity bounded.

From Lesson 3

All four pods fall back for the same hot key. In-process single-flight guarantees what?

Each pod owns its promise map. The database still needs enough capacity for the remaining loads.
