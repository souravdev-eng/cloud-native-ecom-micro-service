Lesson 0 · Day 1 · ~25 min · local lab

Shared state across pods

The first lesson of the course. It covers the idea every later lesson builds on: several copies of a service sharing one Redis, what goes wrong when they all change it, and how to stop it.

Where this course starts

What Redis is

Redis is a database that keeps its data in memory instead of reading it from disk. Memory is fast, so a read or a write takes well under a millisecond. That's why apps use Redis for things they need quickly and often: a cache, a counter, a lock.

Your app talks to Redis over the network, one short command at a time. Every value is stored under a name, called a key. Storing and reading one looks like this:

> SET greeting hello
OK
> GET greeting
"hello"

Why it's in our platform

The product service uses Redis as a cache. It keeps copies of product pages and search results there, so it doesn't have to ask MongoDB every time someone opens a page. Lessons 1–4 look at that cache closely.

Why the course starts here

In Kubernetes, a service can run as several identical copies, called pods, to handle more traffic. Every copy talks to the same Redis. That's what makes Redis useful: one place every pod can see. It's also where the hard problems come from: every pod can change it at the same time. This lesson shows the simplest version of that problem. Every later lesson is a bigger version of it.

How each lesson works

Each lesson tells one short story, asks you to predict what will happen, and runs a lab that breaks something on your machine. Then it explains why, fixes it, and finds the same thing in our code. It ends with a short summary and a quiz. About 25 minutes.

By the end of this lesson you'll be able to:

  • explain why three pods updating one number can lose updates without any error;
  • show it happening, step by step, on your own machine;
  • fix it, and say why the fix works.

The key views holds 10. Three pods each read it, add 1, and write it back, all at the same moment. What can views end up as?

If all three read 10 before anyone writes, all three write 11. If they don't overlap, you get 13. Anything in between can happen too.

Why is INCR views safe when many clients send it at once?

Redis runs commands one at a time. INCR reads, adds and writes inside one command, so nothing else can happen in the middle.

Three pods each keep let views = 0 in memory and add 1 per request. What's wrong?

Each pod has its own memory, so you get three partial counts, and each resets when its pod restarts.

For a small Redis command like GET, what takes most of the time, seen from the app?

Redis runs a GET in microseconds. The request and reply travelling over the network take far longer.

Which single command adds 5 to the number in views?

INCRBY is INCR with a step. DECR and DECRBY count down.

Warm up: your first two commands

One minute. Store a value under a key, then read it back:

npm run redis:cli -- set lab:00:greeting hello
npm run redis:cli -- get lab:00:greeting

The first prints OK, the second hello (some terminals show it in quotes). You've just written to Redis over the network and read it back. Version 2 of the story below does exactly this, just from three pods at once. (Keys starting with lab:00: belong to this lesson, so the lab cleans this one up for you.)

1 · The story: a view counter

The product team wants a small badge on every product page: "Viewed 1,284 times". It's a made-up feature (product doesn't have it), but it's the simplest possible example of many copies of an app sharing one number.

  1. Version 1 · works on your laptop

    You keep the count in a variable inside the product service: views = views + 1 on every page view. With one copy of the service running, the number is right.

  2. Then · three pods

    Traffic grows, so Kubernetes runs three copies of product, called pods. Each pod is a separate program with its own memory, so each has its own views variable. Refresh the page and the badge jumps between three different numbers, depending on which pod answered. Restart a pod and its count goes back to 0.

  3. Version 2 · looks right

    The count has to live somewhere all three pods can reach. That's Redis: one server, one copy of the number. On every page view, each pod now asks Redis for the number, then writes back one more:

    const views = Number(await redis.get(key));
await redis.set(key, String(views + 1));

    You test it by refreshing the page a few times. The count goes up by one each time. Ship it.

Then launch day comes, and thousands of people open product pages at the same time.

2 · Predict

Pick an answer before you run anything. If your guess turns out wrong, that's the useful part: it shows exactly what to look at.

Three pods each count 1,000 page views using version 2 (read, then write back one more). The count starts at 0. What does Redis hold at the end?

Less. Now guess how much less, then run the lab.

3 · See it break

The lab plays launch day. Three workers, each a separate Node program with its own Redis connection, stand in for the three pods. Each adds 1 to one shared counter, 1,000 times, exactly like version 2.

  1. Run it.

    npm run lab:00 -- --broken

Broken: GET + SET · 3 processes × 1000 increments
  expected:          3,000
  counter:           1,000
  lost updates:      2,000 ✗

    Two out of every three page views vanished. Redis didn't report a single error, and every command did exactly what it was told.

    Why exactly 2,000, every time?

    The lab cheats on purpose so it shows the same result every run. Before each write, it makes all three workers wait until each of them has read the counter, like a starting gun. That forces the worst timing every round, and you'll see why it costs exactly two out of three in section 4. Next step, you'll turn the trick off.

  2. Run it the way real life works. Without the starting gun, timing is left to chance:

    npm run lab:00 -- --broken --no-barrier

  expected:          3,000
  counter:           1,392
  lost updates:      1,608 ✗

    Still most of the views lost, but the number changes on every run. Try it twice. A bug like this is easy to miss in testing, because when you test one request at a time, nothing overlaps.

4 · Slow motion

Let's watch a single round, with each worker adding 1 just once. Redis has a command, MONITOR, that prints every command it runs. Open a second terminal for it:

npm run redis:cli -- monitor | grep counter      # terminal 2
npm run lab:00 -- --broken --increments 1        # terminal 1

Among the lines in terminal 2, you'll find these. Here they are as a list, in the order Redis ran them:

  1. Worker AGET counter→ 0
  2. Worker BGET counter→ 0
  3. Worker CGET counter→ 0
  4. Worker ASET counter 1OK
  5. Worker BSET counter 1OK
  6. Worker CSET counter 1OK
  7. Resultcounter = 1wanted 3

All three asked for the number before any of them wrote. All three were told 0, all three worked out 0 + 1, and all three wrote 1. Workers B and C didn't add anything: they overwrote a 1 with another 1.

With the starting gun, every one of the 1,000 rounds goes like this, so three increments become one, and 3,000 becomes 1,000. Stop MONITOR with Ctrl+C when you're done; it slows Redis down.

5 · Why: one whiteboard, one keeper

Here's a picture to keep in your head for the rest of the course.

Redis is a whiteboard in a room with a keeper. Only the keeper may read or write it, and the keeper deals with one request at a time, in the order they arrive.

Version 2 works like this: you walk up and ask "what's the number?" The keeper says 0. You walk back to your desk, work out 0 + 1, walk back, and say "write 1".

While you were walking, two colleagues asked the same question and got the same answer. Each of you does a correct job on your own. Together, you lose two updates.

Each part of the picture is a real thing:

the whiteboard
Redis's memory, the one copy of the number that every pod shares.
the walk there and back
the network. Every command is a message to Redis plus a reply: one round trip.
working it out at your desk
the + 1, which happens in the pod, not in Redis.
one request at a time
Redis really does run commands one at a time, in the order they arrive (Redis docs: "Single threaded nature of Redis").

The problem in one sentence: version 2 needs two visits to the keeper, and other people get their turn in between.

6 · The fix: let Redis do the adding

Don't ask for the number and walk away with it. Ask the keeper to add one. That's one visit: the keeper reads, adds and writes in a single turn, and nobody can get a turn in the middle of it. In Redis, "please add one" is the INCR command:

await redis.incr(key);

  1. Run the fixed version. Same three workers, same starting gun, same worst-case timing. Only the command changes:

    npm run lab:00 -- --fixed

Fixed: INCR · 3 processes × 1000 increments
  expected:          3,000
  counter:           3,000
  lost updates:      0 ✓

    All three workers still hit the counter at the same instant, but now each one takes a single turn. Redis runs the three INCRs one after another: 0 → 1 → 2 → 3.

  2. Let the lab check itself. This runs both versions and confirms what this lesson claims:

    npm run lab:00 -- --check
…
Check
  broken variant loses updates: yes ✓
  fixed variant loses none: yes ✓
  no keys left under lab:00:*: yes ✓
    Is it safe to run the labs?

    Yes. They connect only to the local lab Redis, never to the cluster. Each lab writes only keys starting with its own prefix (lab:00: here) and deletes only those when it's done. No lab ever wipes the whole database.

The same idea comes in other sizes: INCRBY key 5 adds 5, and DECR and DECRBY count down. They're all in the commands sheet.

7 · Now name it

You've seen every one of these happen. Here are their proper names, which the rest of the course uses:

shared state
data that several pods read and change. It has to live outside the pods, in Redis or a database.
round trip
one request to Redis and its reply: the walk to the keeper and back.
read-modify-write
read a value, change it in your code, write it back. Version 2.
race condition
a bug where the result depends on whose turn comes first.
lost update
one write silently overwriting another. What happened to Workers B and C.
atomic
done in one turn, with nothing able to happen in the middle. Every single Redis command is atomic; two commands in a row are not.

The full list is in the glossary.

Isn't Redis multi-threaded now?

Partly. Redis hands some slow chores to helper threads, such as freeing memory and flushing files to disk, and since Redis 6 it can use extra threads to read and write network traffic. But commands still run one at a time on one main thread. The keeper is still alone at the whiteboard.

One person who talks for a long time

"One request at a time" has a cost. If someone asks the keeper for something slow, such as KEYS * (list every key) on a Redis with millions of keys, everyone else waits until it's done. That's why the labs use SCAN, which goes through the keys in small batches. Later lessons come back to this.

Wouldn't it help to send GET and SET together?

Sending several commands without waiting for each reply is called pipelining. It saves walks, but it can't help here: you need the GET's answer before you know what to SET. And even a pipeline isn't one turn: the keeper can serve other people between its commands. When a job doesn't fit a single built-in command, Redis can run a small Lua script as one turn. Lessons 5 and 6 cover that.

The same fix, already in MongoDB

When someone places an order, product lowers the stock. Several product pods can handle orders at once, so this is the view counter's problem with real money attached. Here's how the code does it (product/src/queues/listeners/productQuantityUpdate.ts:24-28):

const updated = await Product.findOneAndUpdate(
  { _id: data.id, quantity: { $gte: data.quantity } },
  { $inc: { quantity: -data.quantity } },
  { new: true },
);
{ _id, quantity: { $gte } }
find this product, but only if it has enough stock.
{ $inc: … }
subtract the amount ordered. The database does the sum, not the app: MongoDB's version of INCR.
findOneAndUpdate
checks and changes the stock in one turn, so no other pod can sneak in between.
{ new: true }
return the product after the change. You can ignore it here.

The comment above this code calls the bug it avoids the "TOCTOU gap", short for time of check to time of use: the walk back from the whiteboard. Lesson 5 comes back here as the right way to protect stock, with no Redis lock at all.

In short: remember these 3

  1. Pods share only what lives outside them. Redis is one whiteboard that every pod reaches over the network.
  2. Read, then write back, is two visits. Other pods get their turn in between, and updates are lost without any error.
  3. One command is one turn. Redis runs commands one at a time, so ask it to do the change for you (INCR) instead of reading and writing back.

If you forget everything: the keeper serves one request at a time, so never walk away with the number.

You don't need to memorise the lab's code, its exact numbers or the node-redis method names. Commands are in the commands sheet, terms in the glossary.

9 · Check yourself

Answer from memory first, then click. You can retry a wrong answer.

With the starting gun on, why did the broken lab lose exactly 2,000 of 3,000?

All three read the same number and write the same number + 1. Each round adds 1 instead of 3, so 1,000 rounds give 1,000.

A teammate says: "Send the GET and the SET together in one go, and the problem disappears." Are they right?

The SET needs the GET's answer, so they can't even go together. And a batch of commands still isn't one turn. Use one command, like INCR.

One client runs KEYS * on a Redis holding 10 million keys. What do the other clients notice?

The keeper serves one request at a time, so a slow one makes everyone wait. Use SCAN, which works in small batches.

What keeps productQuantityUpdate.ts correct when several product pods handle orders at once?

findOneAndUpdate with $inc is MongoDB's INCR: the database does the check and the change in one turn.

Why do the labs refuse to connect to localhost:6379?

With kubectl port-forward open, localhost:6379 is the product cache. The labs only use ports 6390–6399.
