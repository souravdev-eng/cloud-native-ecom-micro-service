Lesson 3 · Day 1 · ~25–30 min · local lab

When everyone needs a new copy

Lesson 2 kept old copies from being read after a change. Now ask what happens when a popular copy disappears and many shoppers need it at once. This lesson is about protecting MongoDB from the work our product pods create on a cache miss.

Before you start

Recall check: Lesson 2 in 2 minutes

From memory: which copies does a product change need to clear? How can a slow reader put an old copy back? What does the edition number fix?

Hint: lists, a colleague walking back, and the number at the top of the board.

Show the answers

Clear every affected copy, including search lists. A reader can load before the write and cache after the delete. Reading a generation before loading, then bumping it after a write, makes that old copy unreachable. The TTL clears abandoned copies and backs up missed invalidations.

Forgot one? Revisit Lesson 2's recap.

By the end, you can reduce repeated loads of one answer, explain the remaining load across pods, and spread a batch of expiries without exceeding your allowed stale window.

Why the failure repeats, and which keys are cleaned

The lab lets the hot key really expire, then holds all workers after their 50 cache reads. No worker can refill until all 200 reads have missed. This forces the worst case even if process startup is slow. Without that starting gun, a late worker could find the first worker's copy and hide the problem.

All keys are under lab:03:*. Cleanup scans and unlinks only that prefix, including on an error. Avoid running two copies of this lab at the same time: they share the prefix.

1 · The question: the sale opens

Imagine a promotion on the Kindle in our shop. This traffic spike is made up for the lab; the cache-aside code is real.

Before the sale, shoppers read the same cached price. MongoDB gets little work. Then the copy reaches its throw-away time. Two hundred shoppers arrive while a fresh read is still on its way back.

Redis answers each GET correctly: there is no copy. What do the four product pods do next?

2 · Predict

All 200 reads miss before a new copy is saved. How many slow-store loads happen with ordinary cache-aside?

Redis only answers GET and SET. It doesn't know MongoDB exists, and it doesn't group app requests. Each request follows the miss path.

4 · Slow motion

  1. The hot key expires. All 200 readers ask for it and get a miss.
  2. Each reader starts a slow load. While those loads run, no fresh copy exists.
  3. They all get 149, save the same answer and respond. A later reader gets a cache hit.

One command being atomic doesn't protect the whole GET → load → SET path. In a real overload, the store gets slower, leaving time for even more misses to join the pile. The fake counts work but doesn't simulate that feedback loop.

5 · Why: a queue at the filing room

Use Lesson 1's picture: the cached price is a photocopy on the whiteboard; MongoDB is the filing room. When the keeper takes down an expired copy, every colleague who sees the empty spot walks to the filing room. Two hundred colleagues ask for the same sheet.

Each team can instead keep a note on its own desk: “Someone is fetching this sheet; wait for their copy.” Fifty colleagues on one team share one trip. Four teams still make four trips, because each team's desk is private.

empty spot
a cache miss after expiry.
one note per sheet
a map from the complete cache key to a promise for the pending load.
one desk per team
each worker's process memory. Redis shares the saved value; it doesn't share a JavaScript promise.

6 · Fix it: wait for the fetch already running

  1. Run the same reads with a shared fetch.

    npm run lab:03 -- --fixed

Fixed: share one fetch inside each worker
  workers:           4
  concurrent readers: 200
  store loads:       4 ✓
  all readers get 149: yes ✓

    One worker starts a load and puts its promise in a map before yielding. Its other 49 readers await that promise. The map belongs outside individual request handlers so all requests in that process can use it. Remove the entry on success and failure; a failed fetch must not poison later attempts.

This protects one hot key inside each process. It cannot promise one load for the whole cluster. If four loads are still too expensive, cross-pod coordination is another layer; Lesson 5 covers leases and their limits. This lesson doesn't add a lock.

A second problem: a hundred copies come down together

Imagine warming a hundred different product copies at startup. Give them the same TTL and their next misses arrive in one wave. Sharing a fetch for one key can't combine reads for a hundred different keys.

    The histogram reads the expiry deadlines stored in Redis. About 100 ms after the base deadline, the lab reads how many keys still exist. The last count can vary with scheduling. It shows actual expiry, not database traffic; keys only cause reloads if someone reads them.

    The fixed batch adds a random offset to each TTL. It uses a fixed seed so you see the same distribution on each run. The lab uses a shared start time and SET … PXAT deadlines to remove write-timing noise. Real cache fills normally use relative EX or PX.

  2. Check the claims together.

    npm run lab:03 -- --check
npm run labs:verify

    The check requires exactly 200 broken loads and 4 fixed loads, all 200 correct replies, clustered expiry without jitter, four occupied buckets spanning at least 1.5 seconds with jitter, and successful cleanup. The verifier runs every lab's check three times.

Jitter spreads different keys over time. One hot key still expires once for everyone. Use both layers. Choose the base and the random range together: if a stale copy may survive at most 60 seconds, 50 + random(0…10) fits; 60 + random(0…10) exceeds the budget from Lesson 2.

7 · Now name it

These names are also in the glossary.

cache stampede
many misses for the same answer start overlapping expensive loads.
single-flight
one pending load per key inside one process; other requests share its result. Also called request coalescing.
TTL jitter
varying expiry times so many keys don't all expire together.
negative caching
keeping a successful “nothing found” answer briefly, so repeated empty queries don't all read the store again.

Soft TTL keeps a copy beyond its freshness deadline: a reader can get that older copy while a coordinated background refresh runs, until a later hard deadline. Only use it where that staleness is acceptable. XFetch probabilistically refreshes before expiry, using the measured rebuild duration and time left; it addresses early refresh rather than randomising the stored TTL. These are further reading, not extra lab variants: see soft TTL and XFetch in Resources.

8 · In our repo: nothing found, every time

From product/src/routes/showProduct.ts, the store read and cache write:

const product = await productApiFeature.executePaginated();

if (shouldCacheResult && product.data.length > 0) {
  const ttl = req.query.search ? calculateTTL(60, "minutes") : calculateTTL(10, "minutes");
  await redisClient.set(cacheKey, JSON.stringify(product), { EX: ttl });
}

res.status(200).send(product);
executePaginated()
queries MongoDB after the cache lookup missed. There is no shared pending-load map around this call.
shouldCacheResult
Lesson 1's policy decides whether this query is eligible for caching.
product.data.length > 0
an eligible search with zero matches never writes a copy. The next identical search misses again.
calculateTTL · SET with EX
fixed 60- or 10-minute TTLs, with no jitter.
res.status(200)
an empty result is still a successful answer, unlike a database timeout or an error.

A design improvement would cache the full successful empty response for a short TTL, for example 15 seconds, using the same complete query key. Check for a cached value with cached !== null; don't confuse an empty result with an absent key. Invalidate it when a new product can make the result non-empty, or accept that short delay. Do not cache a database error as “nothing found”. Bound the number of distinct negative keys: random searches can fill a cache even with short TTLs. This course proposes the change; it doesn't modify product.

In short: remember these 3

  1. A miss can multiply work. Many readers can all fetch the same answer before any saves it.
  2. Share a pending fetch per key. Single-flight brings 200 loads down to one per worker, not one per cluster.
  3. Spread expiries and keep empty answers briefly. Jitter helps batches; negative caching helps repeated empty searches. Neither replaces invalidation or the stale-time budget.

If you forget everything: before walking to the filing room, check whether someone on your team is already fetching that sheet.

You don't need to memorise the seed, histogram counts or XFetch maths. Use the mitigation layers on the caching sheet.

9 · Check yourself

Answer from memory, then click. You can retry.

Four pods use in-process single-flight. All miss the same hot key before any refill. How many loads?

The pending-load map is private process memory. Only the saved cache value lives in Redis.

What does TTL jitter fix?

It spreads deadlines across keys. A single key still has one shared expiry.

Which answer can safely be negative-cached briefly?

Errors aren't evidence of absence. A successful empty result can be reused, with a short TTL and a plan for newly created products.
