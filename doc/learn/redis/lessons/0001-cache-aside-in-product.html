Cache-aside in product

Lesson 0 showed many pods sharing one Redis. This lesson looks at what our product pods actually keep there: copies of product pages and search results. You'll watch that cache work in the real cluster, one command at a time.

What a cache is

A cache is a copy of an answer kept somewhere fast, so you don't have to work it out again. You ask a slow source once, keep the answer nearby for a while, and hand out the copy until it's thrown away.

Why product has one

Products live in MongoDB. It holds the real, up-to-date data; anything else is only a copy of it. Our MongoDB is a hosted Atlas database outside the Kubernetes cluster, even on your laptop, so every question to it leaves the cluster and comes back. Redis sits inside the cluster, next to the product pods, and answers from memory. So product keeps copies of two kinds of answer in Redis:

  • one product: the product detail page, GET /api/product/:id;
  • a list of products: search and filter results, GET /api/product?search=… or ?category=….

Why this lesson comes now

Lesson 0 was about Redis as shared state. A cache is the most common shared state there is, and it's the one our platform already runs. Lessons 2, 3 and 4 each break this cache in a different way (stale copies, a rush of misses, Redis going away). You can't follow those until you've seen it working.

By the end of this lesson you'll be able to:

  • say, step by step, what product does when a page is or isn't in Redis;
  • read a real cache key and its remaining lifetime in the cluster, and explain why search keys look like gibberish;
  • explain why the cache is only ever a copy of MongoDB, and what the expiry time is for.

Warm up: find a product

One minute. Ask for three products, with just their titles:

curl -sk -b cookies.txt 'https://ecom.dev/api/product?limit=3&fields=title'

Keep the quotes: without them your shell treats ? and & as special characters. Pick one product's id and keep it handy. This lesson uses the Kindle, 6950f35901550edc80e88206; your ids may differ. If you get "not authorized" with a 403, the cookie is missing: log in again.

1 · The story: the Kindle page

This is the real product service, not a made-up feature. Only the traffic numbers are invented.

  1. Version 1 · works

    Someone opens the Kindle page. The product pod asks MongoDB for product 6950f…88206 and sends back what it gets. Simple, always correct.

  2. Then · a sale

    The Kindle goes on sale. Its page is opened 500 times a minute, and "kindle" is the most searched word on the shop. Every view is a trip out of the cluster to MongoDB, asking the same question and getting the same answer, 500 times a minute. Searches are heavier still: MongoDB has to find and score every matching product.

  3. Version 2 · what product does today

    Ask MongoDB once, keep a copy of the answer in Redis for a while, and hand out the copy. Fast, and MongoDB gets a break.

  4. The catch · hidden

    Every copy needs a name, so the next request can find it, and an end date. Give two different questions the same name, and shoppers get each other's answers. Keep a copy too long, and it shows a price that's no longer true. Neither one causes an error. Our code has had the first bug already: you'll see it in section 6.

Before you watch it work, a guess.

3 · Watch it work: one product page

  1. Start watching Redis. In terminal 2:

    rcli monitor

    It prints OK and waits. From now on, every command any client sends to the product Redis appears here.

  2. Open the page twice. In terminal 1 (use your own id):

    for i in 1 2; do
  curl -sk -b cookies.txt -o /dev/null -w "detail #$i: %{http_code} %{time_total}s\n" \
    https://ecom.dev/api/product/6950f35901550edc80e88206
done

detail #1: 200 0.079080s
detail #2: 200 0.021425s

    -o /dev/null hides the product itself; -w prints the status and how long the request took. Terminal 2 shows three lines (timestamps and addresses trimmed, the long value cut short):

    "GET" "product:6950f35901550edc80e88206"
"SET" "product:6950f35901550edc80e88206" "{\"title\":\"Kindle Paperwhite (11th Gen)\",…}" "EX" "900"
"GET" "product:6950f35901550edc80e88206"

    Request 1: product looked in Redis and found nothing, went to MongoDB (Redis can't see that part), then stored a copy with EX 900: delete it in 900 seconds, which is 15 minutes. Request 2: it looked, found the copy, and answered. No MongoDB at all, and about four times faster here.

  3. Ask product which way it went. The detail route logs one line per request:

    kubectl logs deploy/product-deployment -c product --tail=2

Return from Mongo...
Return from Cache...

  4. Read the copy and its clock. Stop MONITOR with Ctrl+C (it slows Redis down), then:

    rcli ttl product:6950f35901550edc80e88206
(integer) 889

rcli get product:6950f35901550edc80e88206
"{\"title\":\"Kindle Paperwhite (11th Gen)\",…,\"price\":14999,…,\"id\":\"6950f35901550edc80e88206\"}"

    TTL is the copy's remaining lifetime in seconds: 900 minus the 11 seconds since it was written. Run it again and it has gone down. When it reaches 0, Redis deletes the key, and the next request is a miss again. GET shows the copy is plain JSON text: the product, exactly as MongoDB returned it.

    What do -1 and -2 mean?

    TTL returns -2 when the key doesn't exist (expired, or never written) and -1 when it exists but will never expire. On a cache, -1 is a warning sign: that copy will never be refreshed by itself.

4 · Slow motion: one miss

Here is request 1 again, with the step Redis couldn't see filled in:

  1. productRedis: GET product:6950f…88206→ nil
  2. productMongoDB: findById(6950f…88206)→ Kindle
  3. productRedis: SET product:6950f…88206 {…} EX 900OK
  4. productreply 200 to you79 ms
  5. Next timeRedis: GET product:6950f…88206 → the copy, reply21 ms

Notice who does what. Every row starts with the product pod. Redis never asks MongoDB for anything and doesn't know MongoDB exists. The pod looks, fetches and stores; Redis just keeps what it's given.

5 · Why: photocopies on the whiteboard

Lesson 0's whiteboard and keeper come back, with one new room.

Down the corridor is a filing room with the original documents. It's always right, but it's a long walk.

The whiteboard by your desk holds photocopies. Each one has a label saying what it's a copy of, and a throw-away time written in the corner. When the time comes, the keeper takes it down.

When someone asks you a question, you check the whiteboard first. If the copy is there, you read it out. If not, you walk to the filing room, photocopy the original, pin the copy up with a throw-away time, and then answer. The keeper never walks to the filing room. Only you do.

Each part is a real thing:

the filing room
MongoDB, the system of record: the original data, outside the cluster.
a photocopy
a cached value: the JSON text you saw with GET.
its label
the key: product:6950f…88206. It must cover everything that can change the answer, so two different questions never share a label.
the throw-away time
the TTL: EX 900 when it's pinned up, counting down in TTL.
you
the product pod, which runs all three steps: look, fetch, store.

One thing the picture makes obvious: if someone edits the original in the filing room, the photocopy on the whiteboard doesn't change. It stays wrong until it's taken down. The throw-away time is what limits how long a wrong copy can survive. That's Lesson 2.

6 · Search: the harder label

A product page has an easy label: its id. A search doesn't. The question is everything in the URL: the words, the category, the filters, the sort, the page. Two searches that differ in any of those can have different answers, so they need different labels.

  1. Watch two kinds of list. Start rcli monitor again in terminal 2. In terminal 1, run a text search twice and a category list twice:

    curl -sk -b cookies.txt -o /dev/null 'https://ecom.dev/api/product?search=kindle'      # twice
curl -sk -b cookies.txt -o /dev/null 'https://ecom.dev/api/product?category=other'     # twice
    "GET" "product_search:v2:fbedf1200759f07fadf031101b1efe1f"
"SET" "product_search:v2:fbedf1200759f07fadf031101b1efe1f" "{\"data\":[…]}" "EX" "3600"
"GET" "product_search:v2:fbedf1200759f07fadf031101b1efe1f"
"GET" "product_search:v2:b348b7e87dab38113837b29fd6f05d44"
"SET" "product_search:v2:b348b7e87dab38113837b29fd6f05d44" "{\"meta\":{…},\"data\":[…]}" "EX" "600"
"GET" "product_search:v2:b348b7e87dab38113837b29fd6f05d44"

    The same look, fetch, store, then a hit. Two differences from the product page: the label is a 32-character fingerprint, and the throw-away times differ. A text search lives for 3,600 seconds (60 minutes), the category list for 600 (10 minutes).

  2. Read both clocks.

    rcli ttl product_search:v2:fbedf1200759f07fadf031101b1efe1f
(integer) 3589
rcli ttl product_search:v2:b348b7e87dab38113837b29fd6f05d44
(integer) 589

Where the fingerprint comes from

product writes the whole question down as text, in a fixed order, then runs it through MD5, which turns any text into 32 letters and digits. The same text always gives the same 32 characters; different text gives different ones. For the two searches above:

{"search":"kindle"}     → fbedf1200759f07fadf031101b1efe1f
{"category":"other"}    → b348b7e87dab38113837b29fd6f05d44

Why not use the text itself as the label? A search can carry a dozen filters, so the label would be long and its length unpredictable. The fingerprint is always 32 characters, whatever the question. It isn't a secret or a security measure; it's just a short name for a long question.

A label that left something out

The fingerprint only works if it covers the whole question. Our code once got this wrong, and it's worth seeing why. The old key generator built its text from a fixed list of fields (search, category, price, sort, page and a few more). The quantity filter, "only products with at least N in stock", wasn't on the list. So these two different questions got the same label:

?category=other&quantity[gte]=1    → 20 products
  old key: product_search:a77429ffae891bcf765e34e2b29ca9c3
?category=other&quantity[gte]=60   → 6 products
  old key: product_search:a77429ffae891bcf765e34e2b29ca9c3

Whichever shopper asked first had their answer pinned up. Until that copy expired, the other shopper got it too: 20 products when they'd asked for 6, or the other way round. No error anywhere; just a wrong list. (Those old keys were worked out by running the old code on the side, not read from the cluster.)

The fix, in the code today, has three parts: fingerprint the whole query, not a list of fields; sort the fields first, so the same filters in a different order give the same label; and put v2 in the label, so no pod ever reads a copy pinned up under the old, broken labels. You can watch all three:

  1. Ask three questions. The third is the first one with its filters swapped round. -g stops curl treating the square brackets as special:

    curl -gsk -b cookies.txt 'https://ecom.dev/api/product?category=other&quantity[gte]=1'
curl -gsk -b cookies.txt 'https://ecom.dev/api/product?category=other&quantity[gte]=60'
curl -gsk -b cookies.txt 'https://ecom.dev/api/product?quantity[gte]=1&category=other'

"GET" "product_search:v2:2d6d48fd41e63a6a17ecc193355d0164"
"SET" "product_search:v2:2d6d48fd41e63a6a17ecc193355d0164" "{…}" "EX" "600"
"GET" "product_search:v2:9aa554ee2181aaf86f2a5e4c48bea5ad"
"SET" "product_search:v2:9aa554ee2181aaf86f2a5e4c48bea5ad" "{…}" "EX" "600"
"GET" "product_search:v2:2d6d48fd41e63a6a17ecc193355d0164"

    Two different questions, two labels. The swapped-round question found the first one's copy: a hit, no SET.

What isn't cached?

Not every list goes into Redis. product skips:

  • a plain listing with nothing but limit, sort, fields or page, such as the warm-up's ?limit=3&fields=title;
  • later pages of a category or filter list (the ones with nextKey or prevKey). Later pages of a text search are cached;
  • an empty result. Searching for zzqqxx shows a GET and no SET, so the next identical search goes to MongoDB again. Lesson 3 asks whether that's wise;
  • a product id that doesn't exist (the route returns 404 before it stores anything).

Why three different throw-away times?

The code sets them; it doesn't say why. A fair reading: a text search costs MongoDB the most (find every match and score it), so its copy is kept longest, 60 minutes. Category and filter lists are cheaper, so 10 minutes. A single product is the cheapest of all, 15 minutes. The longer a copy lives, the fewer trips to MongoDB, and the longer it can be wrong after a change. Every TTL is that trade.

Which Redis is this?

k8s/product-redis-depl.yml asks for redis:alpine with no version, so you get whatever is newest when the image is pulled: Redis 8.10 when this lesson was written (rcli info server | grep redis_version). The lab Redis is pinned to 7.4. Every command in this course behaves the same on both. Lesson 7 comes back to why an unpinned version is a risk.

7 · Now name it

You've watched each of these happen. Their proper names, used from here on:

cache hit · cache miss
the copy was there (request 2) · the copy wasn't there (request 1).
cache-aside
the pattern you watched: the app looks in the cache, and on a miss reads the system of record and stores a copy itself. The cache sits aside; it never fetches anything. Also called lazy loading.
system of record
the place that holds the real data. For products, MongoDB.
derived copy
data made from the system of record, which can be thrown away and rebuilt at any time. Every cached value is one.
stale
a copy that no longer matches the system of record: the photocopy of an original someone has since edited. Lesson 2 is about this.
TTL
time to live: how many seconds a key has left before Redis deletes it. Set with EX, read with TTL.
cache key
the label a copy is stored under. It must cover everything that can change the answer.
key prefix
the fixed start of a key, like product: or product_search:v2:, saying what kind of thing it is.
versioned key
a prefix with a version in it (v2), changed when the meaning of the keys changes, so old copies are never read again.

The full list is in the glossary. The pattern and the TTLs are on the new caching sheet.

Why SET … EX, and not SET, then EXPIRE?

Lesson 0's rule again: one command is one turn. SET key value EX 900 stores the copy and its throw-away time together. As two commands, a pod that crashed between them would leave a copy with no throw-away time at all: TTL would say -1, and it would never be refreshed.

Are there other patterns?

Yes. In write-through, the app updates the cache every time it writes to the database, instead of waiting for a miss. In read-through, a caching library does the fetch on a miss so the app doesn't see it. product uses neither. Cache-aside is the most common, and it caches only what someone actually asked for. The caching sheet lists when you'd pick each.

The fingerprint

product/src/utils/cacheKeys.ts:40-48, comments removed:

function generateSearchCacheKey(query: unknown): string {
  const keyString = JSON.stringify(sortQueryValue(query));
  const hash = crypto.createHash("md5").update(keyString).digest("hex");
  return `product_search:v2:${hash}`;
}
sortQueryValue(query)
copies the whole query with its fields in alphabetical order, at every level. That's why the swapped-round question hit.
JSON.stringify
writes the question down as text, such as {"search":"kindle"}.

turns that text into the 32-character fingerprint.
product_search:v2:
the prefix, with the version that keeps old, broken labels out.

The wrapper, and a type that lies

product/src/cache/redisCache.ts:15-18, 20-21, 25, skipping the branch for a caller that passes its own TTL:

public async get(key: string): Promise<string | null> {
  const cachedData = await this.getClient().get(key);
  return cachedData ? JSON.parse(cachedData) : null;
}

public async set(key: string, value: any, ttlSeconds?: number): Promise<void> {
  const serializedValue = JSON.stringify(value);
  // …
    await this.getClient().set(key, serializedValue, { EX: this.calculateTTL(15, "minutes") });
Promise<string | null>
the type promises a string, or nothing.
JSON.parse(cachedData)
but it actually returns the parsed object: the Kindle, not text. TypeScript doesn't object because JSON.parse returns any, which fits any type.
set: JSON.stringify(value)
turns the object into text before storing it. Redis strings hold text, so that part is right.
calculateTTL(15, "minutes")
the default TTL when the caller passes none: 900 seconds.

Why the wrong type matters: a teammate who trusts it writes const raw = await cache.get(key); if (raw) return JSON.parse(raw);. TypeScript is happy, since raw is a string as far as it knows. On a hit it throws: raw is really the Kindle object, which JSON.parse turns into the text "[object Object]", and that isn't JSON. Today's only caller sends the value straight back with res.send, which happens to work for an object, so nothing has broken yet. The honest type would be get<T>(key): Promise<T | null>. That fix, like the others this course designs, is a follow-up ticket, not part of the course.

In short: remember these 3

  1. Cache-aside: look, fetch, store. The product pod looks in Redis; on a miss it reads MongoDB and stores a copy with a TTL. Redis never fetches anything.
  2. The key is the question. A product page is product:<id>; a search is the whole query, sorted and fingerprinted, under product_search:v2:. Leave anything out of the key and two questions share one answer.
  3. The cache is a copy, not the truth. MongoDB is the system of record. The TTL (15 min for a product, 60 for a text search, 10 for other lists) limits how long a copy lives, and so how long it can be wrong.

If you forget everything: check the whiteboard, else fetch from the filing room and pin up a copy with a throw-away time.

You don't need to memorise the fingerprints, the timings or the exact TTLs. The TTLs and the pattern are on the caching sheet, terms in the glossary.

9 · Check yourself

Answer from memory first, then click. You can retry a wrong answer.

MONITOR showed GET, then SET … EX 900, for the Kindle. Where did the MongoDB read happen?

Redis only stores what it's given. The pod got nothing from GET, read MongoDB itself, then sent the copy with SET. That's what puts the cache "aside".

Why are search keys an MD5 fingerprint of the query instead of the query text?

The key has to change whenever the question changes, so it must cover the whole query. The fingerprint is a fixed 32 characters however long the query is. It's a name, not a security measure.

The old key generator ignored the quantity filter. What did shoppers see?

Different questions got the same label, so whoever asked first decided the answer for everyone until the copy expired. A wrong list, with no error.

Since get() says it returns a string, a teammate writes const raw = await cache.get(key); if (raw) return JSON.parse(raw);. What happens on a hit?

It compiles, because the type says string. But get() already parsed the JSON, so raw is an object. Parsing it again turns it into "[object Object]", which isn't JSON, so it throws.

From Lesson 0

Three product pods miss on the Kindle at the same moment. Each reads MongoDB and then SETs its copy. Is that a lost update?

A lost update hurts when each write was meant to add something, like Lesson 0's counter. Here each pod writes the same copy of the same product, so overwriting loses nothing. The real cost is three trips to MongoDB instead of one: Lesson 3's subject.
